# 人群运营模型工程规范

版本 v1.0 · 2026-11-26 · 本项目开发流程的统一来源

## 1. 当前范围与依据

**本项目是服饰零售「人-货-渠」人群运营模型的工程实现**，交付三条需求：本地数据 MCP、货渠匹配工具1／工具2、留存与回购报表集。产品方向与范围见[产品讨论稿 v0.1](产品讨论稿-v0.1.md)；已确认的架构决策（共享匹配内核、移植优先路线）记于该稿的决策记录。

**核心硬约束：业务数据不出网。** 原始导出文件、归一化后的画像索引、模型工件、报表产物全部留在本地文件系统与本地进程内，不上传仓库、不出网、不进入 CI。本项目不是「本地计算所以安全」的假设型项目——每次新增依赖、每次新增出网路径都要按[第 7 节](#7-数据不出网与副作用)显式核对。

**执行依据的优先级**：当前用户确认 → 本变更的规格 → 本规范 → 既有代码与历史推测。发生冲突时以最新明确用户决定为准，并在受影响实施前同步规格。现有代码和聊天推测不能替代已确认需求。

**本规范是开发流程的唯一详细来源。** `AGENTS.md`、工具专属入口和变更规格只放同源指针，不复制完整规则。规范本身不构成依赖升级、数据读取、Git 写入或运行采用的授权。

**继承来源**：本规范借鉴 [OptraCall](https://github.com/gadfly-hbo/OptraCall) 的工程规范骨架（连续 SDD/TDD、独立复核、证据与 Git/CI 精简机制）以及 JuanerAI 的工程质量机制。本项目按自身实际裁剪，裁剪依据与差异见[第 12 节](#12-继承来源与本项目适配)。

## 2. 角色与分工

| 责任主体 | 负责内容 |
| --- | --- |
| 用户 | 确认产品方向、规格、关键口径与重要范围决定；提供业务数据；作出产品验收结论 |
| 执行 Agent | 按规格实施、验证、交付并回执。可由 Qoder／Codex 或其他具备本机写权限的 Agent 承担，同一时刻同一路径只有一个写入者 |
| 独立复核 Agent | 在独立、聚焦的上下文中检查固定候选；不得是该候选任何部分的作者 |
| 业务归口方 | 商品企划、会员算法、渠道运营。本项目提供工具与数据给他们用，不替代其业务判断 |

**本项目与 OptraCall 的关键分工差异**：本项目是**用户直连**模式，不设 PM Agent 发单—领取—回执的 Issue 工单流水线。用户直接确认规格并授权开工，执行 Agent 实施，独立复核 Agent 复核。GitHub Issue 仅作为可选的对外反馈与进度记录载体，不是开工前提。

**并行与写入归属**：并行实现使用各自分支和独立工作目录，避免同目录切分支、重叠写入或覆盖 WIP。同目录协作须先明确不重叠的文件归属。独立复核保持源文件只读，使用隔离验证根。

## 3. 四点产品原则

本项目统一遵循：**Host 管环境、Agent 自主执行、优先复用第三方已有能力、减少人的操作**。

**本项目语境下的具体含义**：

| 原则 | 落地 |
| --- | --- |
| Host 管环境 | Host 负责本地进程、文件读写权限、数据目录只读挂载、端口监听、凭据位置、预算与取消控制、产物持久化；不代业务判断、不补跑计算 |
| Agent 自主执行 | Agent 在授权范围内自主选择方法、工具、执行顺序与纠错方式；不因流程规定被限制在固定步骤或方法配额内 |
| 优先复用第三方已有能力 | 优先复用 ModelEvol 已验证的模型设计与训练管线、model-mlflow 的模型治理账本、抖音工具已验证的评分规则与数据管道；**未经用户授权不改造三方资产本体**，只允许随官方版本升级（升级也要用户授权） |
| 减少人的操作 | 正常使用不应要求用户手工搬运数据、逐条审批普通读取、维护配置或逐次确认。数据接入、口径调整、批量重跑应由工具承担；不可替代的业务取舍才由人做 |

每次规格设计与实现验收都必须实际检查这四点，不能只复述原则口号。检查要求见[第 5.3 节](#53-专项最终检查)。

## 4. 连续 SDD 与 TDD

### 4.1 变更记录

每项非平凡变更在 `openspec/changes/<change-id>/` 维护一份简洁规格与结果记录，首次实际变更时再创建目录。目录用途与文件约定见 [openspec/README.md](../openspec/README.md)。

最少写清：**完整可观察结果、需求／验收标识、范围与不做事项、允许修改路径、关键边界、适用检查、未决问题**。必要设计和证据用链接关联，普通纠错更新原记录，不为每次编辑重建文档套件。

**按复杂度选择规格**：

- 简单、范围闭合的修复可不另建 spec，在适用原记录中留下复现、修正及验证即可
- 跨模块、影响共享内核（见[第 9 节](#9-业务专项约束)）、涉及数据契约、模型资产或公共接口的复杂改动**必须**维护简洁 spec
- 涉及较明显的前端布局、导航或交互流程变化时，先提供可查看的 UI Demo 供用户审核，记录明确审核结果后再实施正式 UI 变更
- 简单的文字修改、按钮调整可不另出 Demo，仍完成相称验证

不把所有修复一律升级为文档／审批套件，也不以「修复」名义绕过复杂变更的必要规格或 UI 审核。

### 4.2 工作顺序

明确目标与验收 → 维护规格并实施适用 TDD → 最小可运行切片与真实路径反馈 → 同一责任方持续修正和受影响检查 → 完整候选集中复核与验证 → 适用验收及获授权 Git 交付。

### 4.3 测试要求

- **确定性行为**：实现前有能检出目标行为错误的测试；修复前保留失败测试或因果复现，再做最小 GREEN 修复和必要重构，留下永久回归。保留关键正向、反向、边界、失败和禁止副作用断言
- **探索与模型质量**：先明确实际任务、预期和观察条件，保留真实试验与失败；不伪造确定性 RED。单次成功只证明该场景及其输入、模型、工具和配置条件
- **纯重构**：保留修改前后 GREEN 与相关等价证据
- **文档和规范变更**：做相称的一致性、引用和范围复核，不制造无意义的占位测试

测试从需求和验收导出，不照着实现重述。环境、导入、定位器或 fixture 失败**不算产品 RED**；后补测试不能伪造历史失败。测试修改或删除应解释覆盖如何保留，不能通过削弱断言把失败改成成功。

**匹配内核的强制回归**：任何触及 `packages/core` 评分逻辑、权重、阈值或维度定义的改动，必须让[黄金校验用例](#93-评分参数变更门禁)全部通过。抖音工具的两条基准用例（¥318.69 短羽绒服 @ 森马服饰号 → 91.9 分 A 级；¥626.83 长羽绒服 @ 森马旗舰店 → 40.9 分 C 级）是最低门槛。

### 4.4 真实路径验证

从首个可运行切片起，尽早走用户正常入口、实际配置、代表输入、真实工具及适用的保存／重开、失败、取消和恢复路径。

需要真实数据、模型或外部副作用的检查，沿用有效授权；**缺少授权时明确标记未验证范围**。Mock、结构校验或导入通过不能证明真实分析成功。

**本项目的真实路径口径**：

| 路径 | 必须实跑 | 可用替身 |
| --- | --- | --- |
| 数据 MCP | 用真实导出文件调用，确认返回画像与指标 | 合成 CSV 可用于单测，不用于验收 |
| 匹配内核 | 用真实商品与渠道画像算分，与人工判断对照 | 合成画像仅用于单测 |
| 工具2 模型 | 真实商品属性 → 预测画像 → 匹配全链路 | 合成属性仅用于管线连通性验证 |
| 报表 | 真实业务数据生成的报表，人工查看可读性 | 合成数据仅用于布局验证 |

### 4.5 任务目标执行清单与范围管理

准备 spec 时一并编写简易的任务目标执行清单，随同提交用户确认。清单顶部写明本轮任务目标和预期交付结果，下面按实际执行阶段拆分任务，为每项写明可核对的完成条件或对应的验收条目。

开工后，对照 spec 和清单推进。每项达到完成条件后立即标记完成，并简记验证结果或链接证据。受阻项保留为未完成，记录原因并继续可推进的项。用户确认调整范围后，同步更新受影响的规格和清单。

1. **以原任务目标和验收为准**。开发中每发现一个新问题，都对照原任务判断它影响哪项验收或使用路径
2. **修复本次引入的回归和直接阻塞**。在现有授权内做最小修复；若需扩大权限、改变公共契约或新增独立功能，先推进可做的部分，把具体阻塞交用户决定
3. **记录范围外问题并继续原任务**。简要记下问题、复现线索及已知影响，留待后续处理。同文件、改动小或顺手可做，都**不足以**作为纳入依据
4. **按原验收核对完成情况**。收尾自检和独立复核逐项核对原验收与清单状态，确认每项额外改动均对应具体回归、直接阻塞或用户已批准的范围变更

### 4.6 阶段门禁

本项目按[产品讨论稿 §8](产品讨论稿-v0.1.md#8-交付节奏建议)的 P0–P4 推进。**未过门禁不进入下一阶段**：

| 阶段 | 门禁条件 |
| --- | --- |
| P0 数据层 | 归一化规则文档完成；真实数据可经 MCP 正确返回；`compare_product_channel` 与 `search_by_tag` 可用 |
| P1 工具1 | 六个匹配维度全部真实计算（无占位分）；黄金用例通过；错配清单可出 |
| P2 工具2 | 跨期验证不低于 v0.4 基线（Top1 69.57% / Top3 91.55% / Share MAE 0.0825，23 款严格留出）；模型包精确版本锁定并登记 model-mlflow |
| P3 报表 | R1–R6 六张报表可生成；三大诊断给出红黄绿灯与归因结论 |
| P4 背对背／面对面闭环 | 双输入比对可产出四大款式分类（共识／盲区／争议／异化）；背对背隔离约束（[第 9.2 节](#92-背对背隔离约束)）经独立复核确认 |

门禁未过时如实记录未达项与原因，不用局部通过表述为全量通过。

## 5. 独立复核与工程完成

### 5.1 独立复核

日常自检、Agent 之间的接口互查和作者测试**不能替代**最终独立复核。复核者不得是该候选任一部分的作者；两位作者互相看代码，不自动构成完整候选的独立复核。

完整结果收尾时固定候选、规格、输入与证据，覆盖 staged、unstaged 和新增文件。提供候选提交或文件清单与摘要、验收依据、允许检查、现有结果、失败和缺口；复核上下文独立，**先从验收导出关键预期**，再检查实现和作者测试。

复核保持源文件、测试、规格和固定证据只读；获准检查需要的临时文件、缓存或报告只能写入明确的隔离位置（如 `.local/`）。复核者独立检查关键路径与失败路径，记录检查范围、命令／结果、发现与结论；作者修复后重验受影响范围。候选变化导致的旧 PASS 失效应明确记录，不能沿用不适用的复核或 CI。

**本项目特别注意**：复核必须在**断网或无真实数据出网**的环境下完成，并核对构建产物的离线可用性。复核者需实际验证「关掉网络后工具仍能跑」这一条，而不只看代码。

独立复核不可用时，明确未完成的复核及其影响；可继续安全、已授权的实现，但**不得用作者自评代替**要求的复核或宣称完整工程验收。

### 5.2 工程完成条件

工程完成至少具备：

1. 当前规格与已确认验收一致，实际修改在授权范围内
2. 适用目标测试、回归与质量检查完成，真实集成路径和结果有证据
3. 独立复核完成，发现已处理；必要的用户风险接受单独记录，不写成复核 PASS
4. 必要 CI 对应实际交付候选；变更到位后更新规格及结果记录，并完成适用归档
5. 交付说明给出版本、验证、失败／未验证项、风险与后续点
6. [第 5.3 节](#53-专项最终检查)的专项检查已通过，或已有负责人批准且仍有效的限范围例外（批准例外不记为检查通过）

产品验收由用户对固定候选作出。工程检查、独立复核、CI、Git 推送、产品验收分别报告；任何一项不自动代替另一项。尚未运行、失败、跳过及未知结果如实保留。

### 5.3 专项最终检查

工程交付的最终验收须包含本项检查，与最终独立复核一并完成。基于本次变更的实际代码、调用链及必要运行记录核对：

- **四点原则**：是否属于环境与治理职责、是否侵入 Agent 自主执行、是否重复第三方／既有能力、是否把可由 Agent 完成的工作推给用户
- **数据不出网**（[第 7 节](#7-数据不出网与副作用)）：新增依赖有无出网路径；构建产物能否离线运行；CI 是否接触真实数据
- **匹配内核唯一性**（[第 9.1 节](#91-匹配内核唯一性)）：是否存在第二份评分逻辑；权重／阈值是否仍单一来源
- **背对背隔离**（[第 9.2 节](#92-背对背隔离约束)）：预测路径是否仍读取人工画像字段
- **模型来源与版本**（[第 8 节](#8-模型与依赖来源约束)）：移植代码有来源标识；模型包版本锁定；失败结论未被复用
- **人的操作**：正常使用无需额外维护／普通读取审批；新增必做动作有目的和必要性证据

验收记录须列明检查范围、候选身份、证据位置、发现的问题，以及「通过／不通过／待验证」结论；不能仅凭设计声明或测试全绿判定通过。检查范围以本次变更及受影响接缝为准，不据此宣称未检查的既有实现已合规。

存在职责越界、重复建设、无合理必要性的新增人工作业或关键证据缺失时，**不得标记本项验收完成**。应修正并复核，或提交写明范围、理由、风险和退出条件的例外供负责人批准。

## 6. Git 与 CI 的精简节奏

### Git

远端为 `https://github.com/gadfly-hbo/user-operation-model.git`，`main` 作为集成基线。一般功能和修复在独立工作分支进行（如 `qoder/<slug>`、`work/<slug>`）；同一分支保持清楚的写入归属。

日常在已有 Git 授权内按需要提交、推送工作分支；内部修正和子任务不必每次创建 PR、全量 CI、独立复核或打包。完整变更收尾时集中一个 PR、独立复核、适用检查和获授权的 squash 合并，再安全快进本地 `main`。

提交前核对实际暂存清单、差异、身份和公开内容；**只纳入本任务文件**。保留 WIP 和失败现场，不重置、清理、强制切换、改写历史或覆盖他人工作。基线变化时检查兼容性，重新验证失效部分。

**数据文件不入库**：原始导出、归一化产物、报表输出、模型工件、MLflow 账本一律不提交。`.gitignore` 是第一道防线，但**不替代内容审查**——提交前逐项核对暂存清单中是否混入业务数据。

推送／合并不自动触发任何数据读取、模型训练或外部服务调用。

### CI

[Check 工作流](../.github/workflows/check.yml) 检查 PR 的实际 head 和每次 `main` push 的实际提交，按变更范围选择校验强度：

| 修改范围 | 验证选择 |
| --- | --- |
| 纯文档（`AGENTS.md`、`README.md`、`docs/`、`openspec/` 下的 Markdown） | 差异格式、UTF-8 编码、引用完整性；不安装无关产品依赖 |
| 已知消费者且影响闭合 | 使用有证据的影响映射运行对应检查，并报告遗漏范围 |
| 运行时、数据契约、匹配内核、模型资产、公共接口、共享依赖、构建／CI 自身或影响不明 | 运行届时定义的完整适用检查及受影响真实路径 |

混合变更只有全部对象被可靠覆盖时才能采用定向检查；否则采用完整适用检查。**检查选择逻辑不能批准自己降级。**

CI 无真实凭据、无模型、无业务数据。所有本地检查与 CI 结果分别记录，浏览器／macOS 真实路径验证与产品验收另行记录。保留失败日志，先解释原因再重试；**无解释的绿色重跑不关闭原始失败**。

## 7. 数据不出网与副作用

这是本项目最高优先级的工程约束，优先于功能便利性。

### 7.1 禁止出网

| 禁止 | 说明 |
| --- | --- |
| 业务数据上传 | 原始导出、画像索引、成交数据、商品图片、报表产物一律不离开本机 |
| 提交到 Git | 包括 `data/` 下的任何文件、CSV／XLSX／JSON 导出物、报表 HTML／Excel 产物 |
| 进入 CI | CI 环境中不得存在任何真实数据副本 |
| 第三方服务调用 | 工具运行期不得调用需要上传数据才能工作的外部 API；不得引入带遥测／上报的依赖 |
| 口径：什么算业务数据 | **款号、店铺编码、SPU 编码等标识符不属业务数据**，可出现在代码、测试与文档中；**属性组合、卖点文案、画像份额／占比、金额与任何数值样本属业务数据**，一律不得入库。标识符不得与属性或文案组合出现（2026-11-28 用户裁定） |

### 7.2 允许的本地行为

- MCP 以 **stdio** 传输，本地进程启动，不监听公网端口
- 本地 HTTP 服务仅绑定 `127.0.0.1`
- 模型包从 `model-mlflow` 的本地导出目录复制，**精确版本锁定**，不引用可变工作区
- MLflow 后端使用本地 SQLite，artifact store 使用本地目录

### 7.3 新增依赖的核对

引入任何新依赖前，逐项确认：

1. 该依赖在运行期是否发起网络请求？是否有遥测？
2. 是否为云服务 SDK 或需要 API Key 上行的组件？
3. 其传递依赖是否引入出网路径？
4. 能否用标准库或既有依赖替代？

**Python 侧特别注意**：`requests`／`urllib`／`httpx` 等在归一化与训练管线中完全不需要，出现即说明管线设计有误。工具2 训练若需 Python，应使用本地文件 IO 与纯数值库。

### 7.4 副作用与未知状态

- Agent 建议、用户采纳、实际执行和效果验证分别记录
- 取消、超时或恢复中不明的副作用保留 `UNKNOWN`，不假定成功，也不盲目重放
- 代码回退**不保证数据回退**；数据兼容性和未知影响需另行核对
- 原始业务文件只读，工具产出的归一化数据与报表是派生物，可安全重建

## 9. 业务专项约束

以下三条来自业务机制，是代码层面的硬约束，不因「先跑起来」而放宽。

### 9.1 匹配内核唯一性

**工具1（事实画像入口）与工具2（预测画像入口）共用同一个匹配内核**，实现于 `packages/core`。

- **禁止复制第二份评分逻辑**。发现重复实现即视为缺陷，不是可接受的临时方案
- **评分参数单一来源**。维度权重、价格带规则、评级阈值、客单惩罚全部在配置中定义，不散落在代码里
- **改动门禁**：触及 `packages/core` 的改动必须通过[黄金校验用例](#93-评分参数变更门禁)，并在规格中记录口径变化影响
- 工具1 与工具2 的差异**只在画像来源**，不在评分逻辑

### 9.2 背对背隔离约束

业务方案要求商品部与会员数据部在企划期**互相看不到对方的预测值**。

- 工具2 的预测路径（商品属性 → 人群画像）**不得读取**商品部人工画像字段（人工定位人群、人工新老客比例、人工推荐渠道、人工 FAB 卖点）
- 预测所依赖的商品属性仅限：品类、版型、面料、工艺、价格带、季节、上新类型、IP —— 即与人工判断**无因果关系**的客观属性
- 人工画像与预测画像的**比对**发生在独立的校对层，不发生在预测路径内
- 该约束须经独立复核确认；违反即导致背对背机制失效，业务价值归零

### 9.3 评分参数变更门禁

权重、阈值、价格带规则或维度定义的任何变更：

1. 跑通全部黄金校验用例并记录结果
2. 在口径报告中说明变化来源（业务依据／数据校准／技术修复）
3. 若为数据校准，提供校准前后对照与回测指标（NDCG@K 等，正匹配定义：售罄率 ≥ 0.6 且退货率 ≤ 0.12）
4. 未经校准的权重调整**不得**标记为「已优化」，只能记为「已调整」

## 10. 证据与进度

源码、长期测试、规格、正式决定和验收结论进入仓库的适用位置。原始命令输出、日志、候选清单和诊断现场保留在任务指定、可供获授权复核者访问的持久位置；数据范围按[第 7 节](#7-数据不出网与副作用)执行。

初始检查可使用被忽略的 `.local/`，**应保留的唯一证据须存入持久位置**（注意：`.local/` 内不得放业务数据）。

记录候选和输入身份、实际命令与退出结果、适用环境／配置、复核范围及失败／未知。重要结论能追溯到验收与可访问证据；不只交摘要或哈希。

进度说明验收推进、实际结果、缺口和下一步，普通里程碑不构成新的审批点。用户明确停止时停止相应任务，保留现场与返回点。
