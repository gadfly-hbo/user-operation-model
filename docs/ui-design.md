## 1. 这次要解决什么

前面做完了 P0 的数据底座与数据 MCP（17 个工具）。现在的问题不是「后端还缺什么」，而是：

已有资产：17 个 MCP 工具、四个平台归一后的画像、归一化规则。
已有参照：`~/Dev/Archive/pls`（森马零售 BI 工作台，归档但未废弃）。

目标：产出一个**可点击的 UI demo** 先对形态，确认后再进正式实现。

## 2. 工作台信息架构

```
人群运营工作台
├─ 决策主线
│   ├─ 选品评审台      ← 核心页：背对背 → 面对面 → 决策
│   ├─ 货渠匹配        ← 工具 1：热力图 + 明细抽屉
│   └─ 新品预测        ← 工具 2：属性 → 画像 + 依据
├─ 数据与画像
│   ├─ 渠道画像库      ← MCP 查询
│   ├─ 商品画像库      ← MCP 查询
│   ├─ 标签反查        ← MCP search_by_tag（人群反过来找货）
│   └─ 数据源管理      ← 17 个工具的就绪状态与缺失原因
└─ 经营
    ├─ 留存与回购      ← 需求三：结构 / Cohort / Recency / 流转 / 诊断
    └─ 复盘飞轮        ← 决策 → 行动 → 反馈 → 复盘
```

**为什么这么分**：pls 的 IA 是「按数据对象分模块」（数据管理／渠道人群／商品人群／人货匹配／新品预测／经营飞轮）。我们**改成按决策流程分**——因为业务方案的主线是「选品评审 → 匹配投放 → 复盘」，不是「先看画像再看匹配」。数据与画像降为支撑区。

## 3. 核心页：选品评审台

这是整个工作台的灵魂，直接对应业务方案 §2.2 的**背对背预测 + 面对面校对**。三栏严格对应三个阶段：

| 栏 | 阶段 | 内容 |
|---|---|---|
| ① 背对背 · 独立产出 | 双方互不可见 | 左：商品部人工画像（可编辑表单）；右：算法预测 Top3 人群包 + 置信度 + 风险旗标 |
| ② 面对面 · 逐维度校对 | 比对 | 六维差异：人工值 ↔ 算法值 + 差异强度条；高度吻合／存在偏离／显著冲突计数 |
| ③ 决策 | 定案 | 建议动作 + 判定理由 + 四类款式对应的动作选择 |

顶部状态摘要直接给**款式分类计数**（共识款／盲区款／争议款／异化款），下方是候选商品表。

**关键设计：两侧产出物物理隔离**。①栏内人工画像与算法画像分上下两块、互不引用，中间用「互不可见」徽标标注——让「背对背」在界面上是可见的约束，不只是文档里的一句话。

### 款式分类与动作的对应

| 分类 | 判定 | 界面给出的动作 |
|---|---|---|
| 共识款 | 画像重合度 ≥ 75% | 放量定单 |
| 盲区款 | 商品部低评价，算法高覆盖高置信 | 小单快反 + 定向测款 |
| 争议款 | 商品部高评价，算法容量不足 | 降级首发 + 要求专属流量资源 |
| 异化款 | 双方看好但人群理解不同 | 修正 FAB，拆多版本详情页 AB 测试 |

判定口径放在 `<details>` 里折叠——默认看结论，需要时再展开依据。

## 4. 与 pls 的融合决策

### 4.1 借鉴（已确认可复用）

| pls 资产 | 借鉴点 |
|---|---|
| AppShell 外壳 | 左侧可折叠导航 208px + 顶栏 48px + 主工作区；移动端侧栏转抽屉 |
| design token 方案 | HSL 中性色 + 亮/暗双主题 + `color-mix` 语义色，40+ 变量可整套搬 |
| 通用组件类 | `.panel` / `.metric-grid` / `.data-table` / `.segmented-control` / `.status-badge` / `.empty-state` / `.drawer` / `.heatmap-table` |
| **`FitExplanation` 四类 tag 证据** | `matched / conflict / missing / lowConfidence` —— 这是「面对面校对」的**语义最小充分集**，我们直接沿用这套证据分类 |
| API 契约的**质量元信息七件套** | `source / sourceType / batchId / timeWindow / sampleSize / confidence / generatedAt`，MCP 返回应带同样信息 |
| 双栏工作台模式 | 左列表 + 右 Inspector（工具1 的热力图 + 抽屉） |
| CSV 导出与列映射解析 | 匹配报告导出、留存报表导出 |

### 4.2 不沿用

| pls 资产 | 原因 |
|---|---|
| 整个 `apps/` 三个应用 | 与 AgentOps / ModelEvol 运行时强耦合；且它自己标注所有 `fitScore` 都是 baseline，非正式公式 |
| `legacyFitScore` | 契约明确要求它永远只是 `diagnostic_reference_only` |
| `data/workspaces/`（141M 运行态） | 运行态产物 |
| `model-calibrated.json` | 明文禁止手工更新后冒充正式模型 |
| `docs/wiki.html` | 已不是任务真源 |

### 4.3 pls 没有、必须新建的

**这是本次设计最重要的结论。** 全仓搜索 `背对背|面对面|校对|并排` 零业务命中——pls 只有「单侧预测 → 与真实画像比对」，**没有双方独立预测再对齐**。

| 能力 | pls 现状 | 我们要建的 |
|---|---|---|
| 背对背 | 无 | 双方各自独立产出，界面上物理隔离，互不可见 |
| 面对面 | 只展示两列 delta | **校对工作流**：人工可改判、留痕、标注依据，形成决策记录 |
| 款式分类 | 无 | 共识／盲区／争议／异化 四分类 + 对应动作 |
| 正式 fit formula | 从未冻结 | P1 冻结；P0 的 MCP 只产出差异不产分数 |

pls 的 `PortraitComparisonWorkbench` 提供了**骨架**（Baseline／Comparison 双列 participant 卡 + 逐维度 delta 表 + 对齐状态徽标），但**没有校对语义**（无 draft / override / attestation）。

## 5. 规范约束在界面上的落地

规范不是文档里的事，在 UI 上有对应表现：

| 规范条款 | 界面体现 |
|---|---|
| §9.2 背对背隔离 | 新品预测页把字段分成「预测可用字段（客观属性）」与「人工侧字段（不进预测路径）」，后者**置灰禁用**并注明原因 |
| §9.1 匹配内核唯一 | `compare_product_channel` 只返回差异，界面**不显示任何匹配分**，避免前端形成第二套口径 |
| §7 数据不出网 | 顶栏「数据就绪 9 / 17」灯 + 数据源管理页逐工具列出缺失原因 |
| DM13 错误路径 | 数据未就位的工具返回明确错误而非空结果，界面显式区分「无数据」与「没接」 |
| 解释型优先 | 每个结论旁都有 `<details>` 展开的依据（差异口径、款式分类规则、评分权重） |

## 6. 数据现状对界面的影响

17 个工具里 **9 个可用、8 个数据未就位**。demo 里如实体现：

- 顶栏常驻就绪灯，不用点进去才知道哪些能用
- 渠道画像库 200 个渠道只有 4 个有画像，列表下方直接写明「其余 196 个暂无人群画像数据」
- 商品画像库同理
- 货渠匹配只有 1 组可比样本，热力图上有一列明显稀疏

## 7. 视觉与密度

### 7.1 视觉论点：一张摊开的对账单

产品的核心机制是**两个独立信源对同一款货做画像，然后把分歧摊在桌面上**。视觉上直接照这个结构来组织，而不是包装成通用后台：

| 元素 | 设计 | 为什么 |
| --- | --- | --- |
| 画布 | 暖纸色 `hsl(38 32% 97%)`，非冷灰 | 商品企划的工作语境是纸样与面料，不是纯数据后台 |
| 人工 / 算法 | 固定双色标记：朱砂 `--human` / 靛蓝 `--algo` | 两侧在整站范围内永远同一个颜色，扫一眼就知道哪边是谁 |
| 背对背 | 两卡之间一道虚线「隔离缝」，竖排「互不可见」 | 让硬约束成为可见的界面元素，而不只是文档里一句话 |
| 面对面 | 差异谱（六维柱状概览，按幅度降序）+ 单行差异行 | 先给整体分歧轮廓，再给逐维证据 |
| 差异行 | 维度 / 人工值 / 强度条 / 算法值 / 差值，单行 | 强度条是连接两个值的「桥」，不是独立装饰 |
| 决策 | 右栏，建议动作大字 + 四类动作单选 | 决策是终点，视觉权重最高 |
| 层级 | 发丝线 + 留白，无阴影 | 纸感来自线与空白，不来自投影 |

### 7.2 密度与字号

- 8px 间距网格；圆角按钮/输入 6px（`--site-radius`）
- **核心指标大数先行**：台账条数值 30px 半粗、单位降级 12px 灰字（`1 款` 而不是 `1款`）
- 正文 13px、元信息 12px；表格行高紧凑
- 每个区块最多一个主按钮，accent 只给真正的主行动
- 工程字段（评分口径、分类规则、隔离说明）一律收进 `<details>`
- 亮/暗双主题共用同一套信息架构与组件尺寸；暗色为暖调黑，不是纯黑

### 7.3 热力图色阶

货渠匹配、Cohort 留存、流转矩阵三处热力图各有自己的**单色序列**，不混用语义色：

- 匹配矩阵：绿序列 A/B/C/D，D 级（<45）单独用红——熔断必须跳出来
- Cohort 留存：蓝序列，颜色深浅直接编码留存率
- 流转矩阵：中性墨序列，对角线（留在原渠道）自然最深

每张热力图都带图例，读者不需要猜色阶含义。

### 7.4 设计变量契约

站点消费 12 个 `--site-*` 变量（背景、前景、强调色、表面、弱化、描边、字体、圆角、间距、字号、动效），可在 Qoder Sites 的 Design Workbench 里整体调节外观而不用改代码。默认值即上述视觉论点。

## 8. 原型说明

`site/web/` —— 纯静态站点，无构建、无依赖、无网络请求（字体走系统栈）。

- 9 个页面，左侧导航切换；支持 `#review` / `#match` 等 hash 直达
- 全部数据为**合成演示数据**，不含任何真实业务数据，也未保留本机目录路径与真实数据规模
- 亮/暗主题切换，记忆到 localStorage
- 交互：候选款切换、动作类型选择、热力图单元格开抽屉、矩阵转置、标签维度联动
- 打开方式：
  ```bash
  python3 -m http.server 8899 --directory site/web
  # http://127.0.0.1:8899/
  ```

已用 Playwright 验证：9 个页面渲染正常、控制台零错误、抽屉开合、转置与标签联动、420px 窄屏无横向溢出、亮暗主题层级一致。验证记录见 `openspec/changes/workbench-ui-site/result.md`。

旧版原型 `docs/ui-demo/` 保留作历史对照，不再维护。
