# 数据样本评估：semir-mvp-samples

> 评估对象：`~/Desktop/待办/semir-mvp-samples`（12 个业务域，30 个文件，3.6 MiB）
> 评估日期：2026-11-26
> 关联：[P0 规格](../openspec/changes/data-mcp-core/spec.md) · [产品讨论稿 v0.1](产品讨论稿-v0.1.md)
>
> **本报告只记录数据结构、字段名与标签体系，不记录任何业务数值、店铺名或经营数据。**

## 1. 总体结论

**这批样本是「完整的数据字典 + 每域一两个样例」，不是可跑通全流程的数据集。**

- **结构层面**：足够。12 个业务域的表结构、字段、标签体系都已明确，归一化层与数据契约可以据此定稿。
- **数据层面**：不足。人群画像只有 1 个实体（某线下门店）的 6 份导出；商品与渠道**只有主数据、没有经营指标**；无生命周期漏斗；无留存回购数据。
- **对 P0 门禁的影响**：DM08（抽样核对）可部分满足，DM12（跨渠道对比）**当前无法验证** —— 只有一个渠道有画像。

**因此结论是：能用，且足以开工 P0-2 / P0-3 / P0-5；但 P0 门禁仍需补数据。**

## 4. 三个必须显式处理的跨平台口径差异

### 4.1 TGI 覆盖不全 —— 修正了匹配分的计算空间

天猫画像**没有 TGI**，只有占比。

**原讨论稿 §4.1 的建议**（"把匹配分升级为 TGI 空间计算"）**在现有数据下不成立**，修正为：

> **匹配分首版在 share（占比）空间计算，TGI 作为独立增强信息单独标注并按平台可比性分级。**

理由：TGI 的绝对值依赖基准人群定义，而天猫侧连 TGI 值都没有。用 share 空间计算可以三平台统一，代价是失去"相对偏好"信息——这个代价在 P1 校准阶段用「平台内 TGI 一致性」检查补。

### 4.2 策略人群：三套命名，同源异名 + 一套独立体系

| 平台 | 字段名 | 取值 |
| --- | --- | --- |
| 抖音 | 八大消费群体 | 新锐白领、都市银发、精致妈妈、都市蓝领、genz、小镇青年、资深中产、小镇中老年 |
| 天猫 | 大快消策略人群 | 新锐白领、都市蓝领、小镇中年、小镇青年、资深白领、Z时代人群、精致妈妈、小镇老年、都市银发族 |
| 京东 | 十大靶群 | 都市家庭、都市蓝领、银发一族、小镇家庭、都市Z世代、都市中产、小镇青年、小镇中产、学生一族… |
| 天猫 | 大服饰策略人群 | 潮流人群、大众实用、低价有颜、低价实惠、品质生活、高阶时尚 |

**前三个是同一体系（泛人群/大快消）的不同渠道命名**：抖音「都市银发」≈ 天猫「都市银发族」≈ 京东「银发一族」；抖音「资深中产」≈ 天猫「资深白领」；抖音「genz」≈ 天猫「Z时代人群」≈ 京东「都市Z世代」。

**天猫「大服饰策略人群」是独立的服饰体系**，与前三个无对应关系。

**处理方式（强制）**：
1. 画像记录**双层结构** —— `platformLabels` 保留平台原值不丢失，`dimensions` 是投影到统一维度集的结果
2. 映射表**显式声明、逐条可追溯**，登记在归一化规则文档
3. **不自动推断未声明的映射**；泛人群与服饰体系之间**禁止互转**

> 这正是 ModelEvol v0.5 的失败点：它做了「跨平台强制映射」，并在同款跨平台时「优先保留抖音画像」，导致渠道语义混淆，被迫在 v0.6 改成天猫独立口径。本项目不复现。

### 4.3 年龄段：三套分档

| 平台 | 分档 |
| --- | --- |
| 抖音 | 18-19、20-23、24-30、31-35、36-40、41-45、46-50、51-55、56-60、60+（10 档） |
| 天猫 | [18,24]、[25,29]、[30,34]、[35,39]、[40,44]、[45,49]、[50,54]、[55,59]、>=60（9 档） |
| 京东 | 0~15岁、16~20岁、21~25岁、26~30岁、31~35岁、36~40岁、41~45岁、46~50岁、51~55岁…（13 档） |

统一目标仍为 5 档：**18-23 / 24-30 / 31-40 / 41-50 / 50+**。

**精度损失必须记录**：天猫 `[18,24]` 横跨抖音 18-19 与 20-23，归并到 18-23 时有边界误差；京东起于 0~15 岁，与其他两家口径不对齐（低龄段无对应）。归一化时保留原始档位，投影结果附带 `precisionLoss` 标记。

## 6. 两项意外收获

**6.1 `08_指标体系` 是指标口径的权威来源**

945 条指标定义含**业务口径、计算公式、维度、基础计量单位、涉密等级、颁发/废止日期**。

需求三报表（R1–R6）的每一个指标——GMV、零售额、零售退款率、售罄率、UPT、连带率——**应当以这份字典的口径为准**，而不是从业务实施方案的文字描述反推。这份字典同时解决了「口径由谁定义」的问题。

**6.2 `12_一条完整业务案例` 给出了端到端关联样例**

`品牌 → 店铺 → 场景 → 款号 → 单品人群画像` 五个实体在同一个工作簿里串起来，字段为：品牌名称、品牌简称、店铺名称、店铺编码、场景名称、场景编码、场景开始/结束时间、款号。

**这正是「人-货-渠」的连接键**，可以作为跨表关联的**黄金用例**：任何新表接入后，都应能在这条链路对上。

## 7. 归属键 A 的验证结果 —— 附带一个发现

**款号确实可作主键，但两份商品主数据几乎不重叠：**

| 表 | 行数 | 唯一款号 | 粒度 |
| --- | --- | --- | --- |
| `商品宽表.xlsx` | 200 | **87** | **SKU 级**（款号×颜色×尺码） |
| `商品-附加字段_modelevol建模用的商品信息表.xlsx` | 257 | 257 | 款号级 |
| **款号交集** | | **仅 10 个** | |

原因不是键失效，而是**两张表覆盖的商品范围不同**（商品宽表首行是某童装品牌的冬季款，ModelEvol 表是某男装品牌的当季 T 恤）。

**同时确认**：`商品宽表` 内部 `款号 → 天猫id` 映射有效（86 条），这是「款号 → 天猫单品画像」的关键桥梁。

**待用户澄清**：这两份商品主数据的关系 —— 是不同商品范围，还是应当有更大的交集？若应有交集，缺口需要补齐。

### 8.1 背对背隔离的具体字段清单

`商品宽表` 中以下字段属**商品部人工定位**，工具2 预测路径必须排除：

| 排除字段 | 理由 |
| --- | --- |
| `年龄段` | 人工人群定位 |
| `商品定位` | 人工定位 |
| `推广群组`、`商品群` | 人工打标 |
| `场景` | 人工场景设定 |
| `延续款`、`主题`、`故事线` | 人工企划决策 |

以下字段属**客观商品属性**，可用于预测：

`货品分类`、`款属性`、`产品链（大类）`、`中类`、`小类`、`年份`、`季节`、`产品季`、`性别`、`吊牌价`、`全域款`、`O2O`、`新老品`、`SKU/SKC/条码`、`天猫id/链接`

`商品-附加字段_modelevol建模用的商品信息表` 的全部 23 列**均属客观属性**（含 FAB、版型、面料、心智产品、IP、特殊功能材质、记忆点、群组打标），可用于工具2 预测。

**`性别修正` 需单独判定**：它是**从历史成交回算的事实修正**，不是人工画像。新款预测时不得使用该款自身的修正值，应从同类历史款推算 —— 这是 ModelEvol v0.6 的既有做法，也是其增益最大的特征。

## 9. 结论与下一步

**可以用。** 结构足以定稿归一化层与数据契约，当前缺口不影响 P0-2 / P0-3 / P0-5 开工。

**但 P0 门禁需要补三样**（按优先级）：商品经营指标、渠道经营指标、多渠道人群画像。

**建议下一步**：

1. 把本报告的四项修正写回 P0 规格
2. 按 A 档表结构先建 `packages/core` 的类型与维度定义（P0-2）
3. 把这批样本放进 `data/` 并补经营指标与更多渠道画像
4. 澄清 §7 的两份商品主数据关系
