## 1. 我们要造什么

**产品是人群运营工作台**：在本机把人、货、渠三侧画像放进同一套坐标系，支撑一条决策闭环——

```
背对背预测 → 面对面校对 → 款式分类 → 组货投放 → 生命周期验真 → 复盘校准
```

工作台由三块能力撑起来（即 v0.1 的三条需求）：

| # | 能力 | 交付物 | 形态 |
| --- | --- | --- | --- |
| 1 | 从消费者视角认识人、货、渠 | **数据服务** | 本地 MCP（stdio）+ 工作台服务共用的一套只读工具 |
| 2 | 模型一：货与渠匹配 | **工具1**（抖音范式）+ **工具2**（ModelEvol 范式） | 工具1 = 规则匹配与看板；工具2 = 可版本化的预测模型 + 匹配 |
| 3 | 模型二：留存与回购 | **报表集** | 本地自包含 HTML + Excel |

**四类用户与他们的活儿**：

| 用户 | 什么时候用 | 要做的决定 | 工作台要给的 |
| --- | --- | --- | --- |
| 商品企划 | 季前企划 | 开哪些款、什么属性、首单多少 | 背对背预测、人工画像录入、面对面校对、四类款式动作建议 |
| 渠道运营 | 上新期、清仓期 | 哪批货配哪个渠道、组货怎么调 | 货渠匹配矩阵、错配清单、渠道画像 |
| 会员／数据部门 | 全周期 | 人群怎么唤醒、往哪个渠道引 | 标签反查、留存／Recency／流转、三大诊断 |
| 管理层 | 月度 | 看健康度 | 大盘人群结构、红黄绿灯与归因 |

**贯穿三块能力的一条主线**：把人、货、渠三侧画像统一成同一套"标签维度 + 占比 + TGI"的数据契约，让商品部的经验画像和会员部的算法画像可以在同一坐标系里比对——这就是业务方案里"背对背预测、面对面校对"能落地的前提。

### 硬约束

- **数据不上云**：所有数据文件、模型工件、报表产物、决策记录全部留在本地；不引入任何外网出网请求。
- **本地优先**：全部通过 `127.0.0.1` 或 stdio 调用，不做公网暴露。
- **可离线**：断网状态下工具链必须完整可用。
- **可溯源**：界面上的每个数字都能追到来源文件、月份、平台与口径版本。
- **留痕**：人工画像、校对改判、决策动作与依据在本机留存，可复盘。

## 2. 总体架构

```
                 ┌──────────────────────────── 本机（Host 管环境）────────────────────────────┐
 浏览器工作台 ───►│  workbench-server（127.0.0.1 + 令牌）                                      │
                 │   ├─ 托管 UI                                                                   │
                 │   └─ 挂载工具注册表 ──┐                                                        │
 Agent 客户端 ───►│  data-mcp（stdio）──┤                                                        │
                 │                     ▼                                                        │
                 │        工具注册表（名字 + 入参 schema + handler，传输无关）                 │
                 │                     │                                                        │
                 │        应用服务：选画像 · 匹配编排 · 预测编排 · 评审流程 · 诊断 · 报表 · 健康  │
                 │                     │                                                        │
                 │        领域核心（纯函数，packages/core）                                    │
                 │   内核 · 相似度 · 期间与画像选择 · 身份解析 · 款式分类 · 诊断规则 · 校准      │
                 │                     │                                                        │
                 │        数据访问：来源目录 → 解析 → 归一化 → 索引（时间感知 + 血缘 + 健康）     │
                 │                     │                                                        │
                 │        本地持久化（全部不入库）                                               │
                 │   data/（只读输入）· workspace/（评审与决策）· models/（模型包）· 输出产物     │
                 └──────────────────────────────────────────────────────────────────────────┘
```

这是**目标架构**。现状与差距的逐项证据见[底层架构梳理与重构方案 v1](architecture-review-v1.md)，到达路径见 §8。

**关键架构判断：工具1 和工具2 不是两个独立工具，而是同一条链路的两个入口。**（D1）

| | 工具1 | 工具2 |
| --- | --- | --- |
| 输入的商品画像 | **已有的真实成交人群画像**（抖音/天猫导出） | **商品客观属性**（品类/版型/面料/价格带…） |
| 画像来源 | 事实数据 | 算法预测 |
| 回答的问题 | 「这批货该配哪个渠道」 | 「这批货会卖给谁、该配哪个渠道」 |
| 覆盖范围 | 已上市有成交的款 | **未上市的新品** |
| 对应业务环节 | 面对面校对 | 背对背预测 |
| 技术范式 | 专家规则评分 | 可训练 + 可版本化的模型 |

这个分工不是我们发明的，是业务方案里"背对背"机制的必然要求：会员部要在**看不到商品部人工画像**的前提下独立预测，只能从商品属性出发。所以工具2 必须具备"属性 → 画像"的能力，否则背对背无从谈起。

**两个工具共享同一个匹配内核**：画像 → 六维匹配分 → A/B/C 评级。差异只在画像从哪来（事实 vs 预测）。

**工具2 现阶段的两条如实说明**（详见梳理报告 §4.9 与附录 C）：

1. 已登记的 v06 模型在归档数据上的科学门槛结论是 `FAIL_NOT_POSITIVE`——相对「账号平均画像」基线没有显著优势。真实数据到位重训前，它只能当实验基线（D8）。
2. v06 模型输出的是天猫原生六维，其中「大服饰策略人群」不是内核主干维度，而内核权重最大的「策略人群」它并不预测。预测画像进内核时，五个分布维度只有四个可用。

## 3. 需求一：数据服务

### 3.1 数据域设计

按《零售服饰人群运营模型》第一章的三段结构设计，落到具体数据实体。

#### 渠道画像（渠）

- **渠道信息**：渠道 ID、渠道类型（直播 / 商品卡 / 短视频 / 天猫 / 京东 / 线下门店 / 私域小程序 / 唯品会特卖 / 奥莱）、渠道定位、平台人群画像、所属层级（品牌 → 渠道 → 账号）
- **渠道人群画像**：与商品侧**完全相同的维度集**，标签 + 占比 + TGI + 样本量 + 画像覆盖率 + 统计月份
- **渠道经营指标**：成交额、成交件数、件单价、转化率、客单价、流量成本（部分渠道缺）、毛利率

#### 货品画像（货）

- **单品基础信息**：SPU 款号、商品 ID、名称、品类（一级/二级）、季节、上新类型、价格（吊牌价 / 企划件单价 / 零售额 / 零售量 / 真实成交单价）、件数、版型、面料成分、设计工艺、IP/联名、FAB 三层拆解（Feature / Advantage / Benefit）
- **货品人群画像**：单款人群画像（各维度 share + TGI）；品类／系列／爆款／IP 聚合画像
- **生命周期行为漏斗**（对应方案三阶段）：上新期 T+0~30（浏览、收藏、加购、购买、直接购买）；增长期 T+31~75（收藏、加购、购买、直接购买、退货）；清仓期 T+76+（购买、退货）
- **经营指标**：零售额、零售量、零售折扣、毛利率、退款率、退货率、UV、转化率、售罄率、缺码率、UPT、新老客占比

#### 人群画像（人）

- **品牌目标人群画像**（企划定义的目标）；**品牌全域人群画像**（实际成交沉淀）；**竞品人群画像**
- **会员特征字典**（方案 §5.2 的字段集）：体型版型（主力穿着尺码、版型宽容偏好、尺码退货敏感度）；风格审美（主风格圈层、色彩接受度、设计细节敏感度、IP 偏好）；时令节律（新品尝鲜倾向、跨季换新心智、生命周期状态、连带穿搭潜力）；价格渠道（折扣敏感度、首选成交渠道、全域流转特征）；行为派生（RFM 属性、类目偏好、渠道偏好）

### 3.2 统一标签维度集

这是三方能对话的关键。**商品侧、渠道侧、人群侧共用同一套维度命名**，否则匹配分无从计算。

| 维度 | 标签类型 | 说明 |
| --- | --- | --- |
| 预测性别 | 分类 | 男/女占比 |
| 预测年龄段 | 分类 | 三平台原档位 → 归并 5 档（18-23 / 24-30 / 31-40 / 41-50 / 50+），保留原始档位与精度损失标记 |
| 策略人群 | 分类 | 八大消费群体／大快消策略人群／十大靶群（泛人群体系）；天猫大服饰策略人群属独立体系，禁止与泛人群互转 |
| 预测消费能力 | 分类 | 低/中/高消费占比（客单承接的输入） |
| 城市等级 | 分类 | 一二三四线 |
| 预测人生阶段 | 分类 | 学生/职场/家庭等（京东源数据无此维度） |

补充维度（方案 §5.2 的风格/价格/渠道类）在会员特征字典层落地，暂不进入首版匹配分。

**统一表示**：

```ts
type Portrait = {
  entityType: string;                       // product / channel / brand / competitor …
  entityId: string;
  period: { kind: 'month' | 'window' | 'year' | 'unknown'; label: string };
  platformLabels: Record<string, Record<string, Record<string, PortraitLabel>>>;  // 平台 → 原生维度 → 标签
  projections: Record<string, { dimension: string; labels: Record<string, PortraitLabel> }>;  // 统一维度投影
};
```

画像采用**双层结构**：`platformLabels` 保留平台原值不丢信息，`projections` 是投影到统一维度集的结果；映射表显式声明、逐条可追溯，未声明的不推断。

### 3.4 技术形态

- **协议**：MCP over stdio 供 Agent；工作台服务只绑 `127.0.0.1`、带令牌；两者挂同一套工具注册表。
- **实现语言**：TypeScript / Node ≥ 22.19。
- **数据层**：只读挂载本地数据目录；索引在内存（规模：万级商品、数十渠道、百级标签），**时间感知**（月份是一等公民），带来源与健康信息；不落库、不入 git。
- **数据源接入**：业务侧按模板包（`templates/数据模板.xlsx`，由代码契约生成）提供文件 → 来源目录识别 → 归一化 → 索引。文件识别规则只有一处来源。
- **缺失语义**：不插补、不回退相邻月份、多份画像时显式报歧义；数据未到位的工具返回明确错误并指名缺哪个文件。

## 4. 需求二：两个工具

### 4.1 工具1 —— 规则匹配看板（参考抖音货渠匹配）

**定位**：不训练、开箱即用、给商品企划和渠道操盘手做日常选品排期。

**核心逻辑**（六维加权，唯一实现在 `packages/core/src/match`）：

```
单维度分 = 100 × (0.60 × JS 相似度 + 0.25 × 余弦相似度 + 0.15 × Top3 重合度)
综合分   = Σ(维度分 × 权重) / Σ(可用维度权重) + 客单惩罚 → 四舍五入 1 位小数 → 裁剪到 [25, 99.5]
评级     ：A ≥ 80 | B 60–79.9 | C < 60；熔断 < 45 只做显示标记
```

v0.1 列出的抖音工具三个缺陷已修：地域同频与品类共振两个占位分换成城市等级与预测人生阶段两个真实维度；分布距离换成 JS／余弦／Top3 混合；权重与阈值全部进配置。按 D5，比较只在双方都有的标签上进行。

**客单承接规则**（抖音工具最成熟的部分，保留为可配置表，见 `docs/match-kernel.md` §3）：按商品价格区间 × 渠道高／低消费占比给出维度分与全局扣分。

**输出形态**：按渠道选品；一货配全渠；深度比对（六维雷达 + 客单断层预警 + 运营建议）；**错配清单**（按 `零售额 × (1 - 匹配分)` 排序的"高销售低匹配"清单）；交叉矩阵。自包含静态 HTML + 可选 CSV 导出。

**如实说明**：权重未经真实成交数据校准，只能记「已调整」，不得称「已优化」；校准回测（用售罄率 ≥ 0.6 且退货率 ≤ 0.12 定义正匹配、算 NDCG@K）是后续独立变更。

### 4.2 工具2 —— 可版本化的人货渠匹配模型（参考 ModelEvol）

**定位**：面向"新品还没有任何成交数据"的场景，是背对背预测的技术载体。

**ModelEvol 的资产取舍**（不变）：v0.4 的 Ridge、跨期验证协议与特征集——移植；v0.6 训练管线骨架（固定 fold、折内词表、账号均值基线、OOF、消融、显著性检验、fail-closed 校验）——移植；v0.7 结论、v0.5 跨平台混合口径、26Q4 未回测预测——不继承；号货匹配评分卡——移植为共享内核；P0 baseline 的 outcome-aware 评估设计——移植思想，回测数据不当已验证模型引用。

**移植时修掉的问题**（已落地）：绝对路径改配置注入；Ridge／解析／指标抽公共库并纳入类型检查；不继承 `xlsx@0.18.5`；untracked 文件先固化并写明来源。

**首版模型形态：路线 A（移植优先）—— D2**。执行要点：移植 v0.6 训练骨架 + v0.4 特征集与跨期验证协议；重训产出按 Studio 契约导出为自包含 `predict.mjs`；**验收线**：同一套跨期验证协议下不低于 v0.4 基线（Top1 69.57% / Top3 91.55% / Share MAE 0.0825，23 款严格留出）；训练管线保持可插拔，后续可换成 Studio 训练。

**现状（2026-11-28）**：移植与登记已完成（v1／v2 均为 Staging）；生产门用的合规基线为 0.7754 / 0.9300 / 0.0759（归档数据上，不可外推）；科学门槛 `FAIL_NOT_POSITIVE`。因此（D8）工具2 在工作台里标「实验基线」，并且要补上「预测画像 → 匹配内核」的消费链路——这是底座重构切片 E 的内容，其接口事实见梳理报告附录 C。

**业务侧产出（对应方案 §2.2 四大款式决策矩阵）**：工具2 的输出要能直接映射到四类款式——共识款、盲区款、争议款、异化款。这要求预测画像与人工画像**可比结构一致**；v06 模型目前不预测策略人群，这一点在重训时要补。

### 5.2 三大诊断的判定逻辑（方案 §5.3）

1. **二回断崖**：大促引入大量新客，但第 60 天二回跃迁老客比例 < 10% → 判定首购客群低质或首购体验有缺陷，倒查 FAB 与版型。
2. **虚假繁荣**：老客回购数大幅上涨，但增长全部来自 Recency > 180 天的休眠召回客，且平均毛利率 < 30% → 判定过度依赖深折透支心智，正价健康回购未改善。
3. **清仓客次季跃迁**：清仓新客在次季正价新品的购买转化率 → 反向校验清仓打法的 LTV 价值。

三条诊断在报表里以**红黄绿灯 + 归因结论**呈现，而非只有数字。指标口径以《指标字典-品牌经营业务》为准。

### 7.1 画像记录

type PortraitLabel = { share: number; tgi?: number };   // tgi 可缺，缺失不等于 0
type Portrait = {
  entityType: string;                                  // product / channel / brand / competitor …
  entityId: string;
  period: { kind: 'month' | 'window' | 'year' | 'unknown'; label: string };  // 'YYYY-MM' / 'YYYY-MM~YYYY-MM'

  projections: Record<string, { dimension: string; labels: Record<string, PortraitLabel> }>;

### 7.2 商品档案（对齐方案 §5.1 的 Single SPU Dossier）

```ts
type ProductDossier = {
  schemaVersion: '0.2.0';
  spu: string; id?: string; name?: string;
  category?: { l1?: string; l2?: string; l3?: string };
  season?: string; launchType?: string;
  price?: { tagPrice?: number; unitPrice?: number; discount?: number };        // 主数据里的静态价
  fab?: { feature?: string[]; advantage?: string[]; benefit?: string[] };
  attributes?: Record<string, string[]>;                                        // 完整字段集（档案，不是预测输入）
  predictionAttributes?: Record<string, string[]>;                             // 预测路径可见子集
  comparisonOnly?: Record<string, string[]>;                                    // 仅比对层可见的人工定位字段
  portraits?: Array<{ month: string; platform: string; projections: … }>;     // 全部月份或指定月
  performance?: Record<string, PerformanceMetrics>;                             // 月份 → 指标
  funnel?: Record<string, Record<'launch' | 'growth' | 'clearance', Record<string, number>>>;
  channelPerformance?: Record<string /*渠道*/, Record<string /*月份*/, { retailAmount?: number; retailQty?: number }>>;
  extra?: Record<string, unknown>;
};
```

真实成交单价由 `resolveUnitPrice(product, month?)` 一处推导：该月经营指标的零售额 ÷ 零售量优先，其次主数据的成交单价、件单价；都没有就记缺失，不插补兜底价。

### 7.3 画像差异与偏离度（业务方案 §2.2 核心）

```ts
type DimensionDiff = {
  dimension: string;
  productTop3: { label: string; share: number; tgi?: number }[];
  channelTop3: { label: string; share: number; tgi?: number }[];
  distance: number; overlapTop3: number; jsSimilarity: number; cosine: number;
  excludedProductLabels: string[];   // 单侧独有、未参与比较的标签
  excludedChannelLabels: string[];
};
```

### 7.4 匹配内核统一公式（工具1/工具2 共用）

```
单维度分 = 0.60 × JS相似度 + 0.25 × 余弦相似度 + 0.15 × Top3重合度     （都在公共标签的重归一化分布上算）
维度分   = 单维度分 × 100；缺维度或无公共标签时剔除，剩余维度重归一化
综合分   = Σ(维度分 × 维度权重) / Σ权重 + 客单惩罚
评级     = A (≥80) | B (60–79.9) | C (<60)
```

维度权重（初值，未经真实数据校准）：预测性别 0.10 | 预测年龄段 0.20 | 预测消费能力 0.15 | 城市等级 0.10 | 策略人群 0.25 | 预测人生阶段 0.20。参数的唯一来源是 `packages/core/src/match/config.ts`。
