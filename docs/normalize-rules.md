## 2. 实体标识与月份

### 2.1 月份写法

| 写法 | 归一化结果 | 例 |
| --- | --- | --- |
| `YYYY-MM` | 原样 | `2026-10` → `2026-10` |
| `YYMM` | 补全世纪 | `2610` → `2026-10` |
| `YYMM-YYMM` | 区间 | `2507-2606` → `2025-07~2026-06` |
| `YYYY` | 全年区间 `YYYY-01~YYYY-12`，标 year（近似） | `2024` → `2024-01~2024-12` |

月份不合法（如 `2026-13`）返回 `null`，**不猜测**。年份不再伪装成该年 1 月（R-7）。

### 2.2 实体标识来源

按优先级：

1. 调用方显式传入的 `entityId` / `month`
2. 抖音画像：**CSV 表头列名**（`<起止年月><实体名>-占比`）
3. 天猫／京东：**文件名**（`<年份|月份>_<实体名>_<平台>`、`透视分析_<月份>_<实体名>_<平台>`、`款号<款号>_<平台>`）

文件名切分**只按下划线**，避免把 `2507-2606` 这类月份区间拆开。

实体名解析后还要做两级清理，见 [§2.3](#23-实体名的两级清理)。

### 2.3 实体名的两级清理

平台画像的实体名来自文件名或 CSV 列名，常带噪声。不清理会导致**同一实体在不同平台得到不同 entityId**，无法关联。解析后做两级清理：

| 级别 | 处理 | 例 |
| --- | --- | --- |
| 1 | 按 `_` 分段，去掉其中**任意位置**的**平台后缀段**。中文项：抖音／天猫／京东／小红书／拼多多／快手／唯品会／淘宝／得物／视频号／微信／线下／实体店／直播／线下门店；英文项：douyin／tmall／jd／xhs／pdd／ks／vip／taobao／offline。全部分段都被识别为平台后缀时保留原样 | `演示账号1画像数据_天猫` → `演示账号1画像数据` |
| 2 | 剥掉末尾的**噪声词**（`画像数据` / `人群画像` / `人群数据` / `画像` / `数据` / `明细`），可反复剥离 | `演示账号1画像数据` → `演示账号1` |

清理后仍保留有区分度的中文实体名（如「森马广州越秀区北京路店」不被误伤）。

### 2.4 实体别名（跨期关联）

**已知问题**：同一实体在不同时间段的导出，实体名可能不一致（示例：某门店两个时段的导出文件名一处含完整门店名、一处为简称）。直接按 entityId 关联会导致跨期断裂。

处理：

- 实体 ID 按 §2.3 清理后保留；**跨期别名合并由别名目录驱动**（见 §12.4）
- **不自动按相似度合并实体**——同名不同店、简称相同实体等情况必须人工确认
- 别名目录只做**实体名归一**，不做画像内容合并

## 3. 字段映射规则（商品与渠道）

### 3.1 落位由字段目录驱动

`packages/core/src/product/catalog/fields.ts` 的每个条目声明 `key` 与 `sources`（源列名候选）。归一化按列名反查字段，**新增源列不需要改归一化代码**。

| 源表 | 列覆盖 | 未登记列 |
| --- | --- | --- |
| 商品宽表 | 47 列**全部登记**，无遗漏 | 无 |
| ModelEvol 属性表 | 23 列**全部登记**（含 `品类` → `category_l3`、`销售季备注` → `sales_season_note`） | 无 |
| 渠道宽表 | 14 个字段直落 `ChannelRecord`，其余 20 列进 `attributes` | 无 |

**字段目录当前 68 个字段**（其中 **33 个**被排除在预测路径之外）。后续数据源出现新列时：能归入既有字段的加进该字段的 `sources`，不能归入的新增一条 `FieldSpec`。两者都不需要改归一化代码。

### 3.2 SKU 级去重

商品宽表是 SKU 级（款号 × 颜色 × 尺码）。归一化按款号去重：

- **保留首行**，其余行记 `conflict`（warning）并说明已去重
- 不做跨行字段合并——不同 SKU 行的同名字段值可能不同，合并规则需另行定义

### 3.3 数值与文本

| 字段类型 | 处理 |
| --- | --- |
| `number` | `parseNumber`，空值／`-` → 不落位 |
| `string` / `text` | 原样去空白 |
| 空值 | **不落位**，不做默认值填充 |

价格类字段（吊牌价、零售额、零售量、件单价、折扣）落入 `ProductDossier.price`，同时保留在属性集中。

## 4. 画像投影规则

### 4.1 三种投影模式

由维度目录的 `projection` 字段决定：

| 模式 | 适用 | 规则 |
| --- | --- | --- |
| `mapping` | 六维主干 + 服饰体系 | 按跨平台映射表对齐到统一词表；无映射的标签**不投影** |
| `bands` | 年龄段 | 按有序分档归并规则投影；无对应的档位**不投影** |
| `identity` | 扩展维度 | 沿用平台原值，仅归并维度 |

### 4.2 原生维度定位

维度目录的 `sourceDimensions` 登记**精确**原生维度名，`sourceDimensionPatterns` 登记**通配模式**（`*` 匹配任意串），用于覆盖无法穷举的同族维度（如天猫各品类「…价格段偏好」）。

优先级：**精确匹配 > 通配匹配**。已被精确匹配的原生维度不再被通配模式接管。

### 4.3 标签命名空间

当同一目标维度在同一平台有多个原生来源，或该来源由通配模式匹配而来时，目标标签带**原生维度名前缀**：

```
category_price_band: { '奶粉价格段偏好·0-49元': {...}, '彩妆价格段偏好·0-29元': {...} }
```

不这么做会让不同原生维度的同名标签互相覆盖。

### 4.4 占比合并

同一目标标签被多个源档位命中时（如年龄归并）：

- **占比直接相加**
- **TGI 按占比加权平均**：`tgi = Σ(tgiᵢ × shareᵢ) / Σ(shareᵢ)`；缺 TGI 的项不参与平均

### 4.5 跨边界源档的拆分

源档横跨目标档边界时（如天猫 `[18,24]` 横跨 `18-23` 与 `24-30`），**不能把全部占比记入主档**——那会让主档系统性偏高、次要档系统性偏低（京东 `24-30` 曾因此偏低约两成）。

拆分依据是**源档闭区间与目标档闭区间的重叠整数岁数**：

| 源档 | 区间 | 拆分结果 |
| --- | --- | --- |
| 天猫 `[18,24]` | 18–24（7 岁） | `18-23` 得 6/7，`24-30` 得 1/7 |
| 天猫 `[30,34]` | 30–34（5 岁） | `31-40` 得 4/5，`24-30` 得 1/5 |
| 京东 `21~25岁` | 21–25（5 岁） | `18-23` 得 3/5，`24-30` 得 2/5 |

源区间未被任何目标档覆盖的部分，并入**距离最近**的目标档（占比守恒），该规则同时标 `partial` 提示精度损失。差距过大（如童装 0–15 岁）时规则本身为 `unmapped`，不参与拆分。

每条年龄规则在目录中声明 `sourceRange`，拆分不依赖任何硬编码。

### 4.6 占比与 TGI 的解析口径

| 平台 | 原始写法 | 处理 |
| --- | --- | --- |
| 抖音 | `39.26%` | 除以 100 → 0.3926 |
| 天猫 | `71.20%` | 除以 100 → 0.7120 |
| 京东 | `0.6` | 原值 0.6（已是小数） |

规则：**含 `%` 则除以 100，否则按原值**。

TGI 一律按原值，不做换算。**缺失返回 undefined，不补 0**——天猫根本没有 TGI 列，缺失与 0 是两回事。

## 5. 跨平台映射规则

### 5.1 映射表

`packages/core/src/portrait/catalog/mappings.ts`，77 条，每条带：

| 字段 | 作用 |
| --- | --- |
| `id` | 唯一标识，可回溯 |
| `platform` | 源平台 |
| `sourceDimension` / `sourceLabel` | 源原生维度名与标签值 |
| `targetDimension` / `targetLabel` | 目标统一维度与标签 |
| `confidence` | `exact` 同名同义 / `manual` 人工判定 / `derived` 规则推导 |
| `status` | `confirmed` 参与投影 / `needs-confirmation` **不参与投影** |

### 5.2 禁止跨体系互转

两个体系族（`family` 字段）：

| 族 | 维度 | 来源 |
| --- | --- | --- |
| `general` | `strategy_segment` 策略人群 | 抖音八大消费群体／天猫大快消策略人群／京东十大靶群 |
| `apparel` | `apparel_segment` 服饰策略人群 | 天猫大服饰策略人群 |

**两族之间禁止互转。** 校验在**构造期强制**：`MappingTable.add()` 一旦加入跨族映射即抛错并拒绝入库，不依赖运行期再调用 `validate()`。`validate()` 保留为审计接口。

**源维度必须已登记**：映射的源原生维度名必须在维度目录的 `sourceDimensions`／`sourceDimensionPatterns` 中登记，否则无法判定体系族，该映射同样在 `add()` 时被拒绝。

理由：泛人群体系描述的是通用社会分层（都市蓝领、精致妈妈），服饰体系描述的是价格带与风格偏好（潮流人群、低价实惠），二者语义不同、粒度不同，强行对齐会产生虚假的人群等价。

### 5.3 未映射组合不推断

源组合（平台 + 原生维度 + 原生标签）没有已确认映射时：

- **不投影**，标签保留在 `platformLabels`
- 归一化问题清单记 `unmapped-value`（warning）
- 映射表缺条目时**只提示、不自补**

### 5.4 待确认映射

映射的 `status` 为 `needs-confirmation` 时**不参与投影**，保留在 `platformLabels` 中。

**当前没有待确认的映射**。天猫「预测购买力」L1–L5 的方向已由用户确认（2026-11-26：**L1 最低购买力，L5 最高**），5 条映射转为 `confirmed`，天猫的消费能力维度已正常投影。

未来若出现方向不明的映射，按同样的方式标记 `needs-confirmation`，待确认后只改 `status` 字段即可生效，不需改代码。

### 5.5 统一词表是三平台并集

`strategy_segment` 的统一词表 14 个标签是三平台的**并集**。各平台实际只覆盖其中一部分（抖音 8 个、天猫 9 个、京东 10 个，另有 6／5／4 个标签在某平台不可达）。

**匹配口径**：比较两个实体时，只在**双方都存在的标签**上计算距离；单侧独有的标签不计入差异，但也不被当作 0。该口径在 P1 匹配内核落地时固化。

**实现说明**（切片 A · SA-06 落实，2026-11-28）：JS 距离、余弦与 Top3 重合度都在**公共标签的重归一化分布**上计算——把双方标签交集各自归一化后再比；被排除的单侧标签记录在 `excludedProductLabels`／`excludedChannelLabels`。某维度双方没有公共标签时该维度不可用（`no-common-labels`），不参与加权。这是技术修复而非数据校准（配置仍记「未校准」）。**share 为 0 的标签**（复核修正补充）：双侧都有记录、份额为 0 的标签是「观测到的 0」，仍算公共标签参与计算；只有单侧无记录的标签才作为单侧独有被排除。

### 5.6 聚合口径（品类层级）

`get_portrait_aggregate` 把**多个商品**的画像聚合成一个层级画像（当前支持品类层级）。

| 项 | 口径 |
| --- | --- |
| 成员范围 | 该品类下**有画像**的商品；无画像商品不计入成员 |
| 维度集合 | 所有成员画像维度的**并集** |
| 占比 | 各成员的占比**算术平均**（成员等权） |
| TGI | 各成员的 TGI 按其占比**加权平均**：`Σ(tgiᵢ × shareᵢ) / Σ(shareᵢ)`；成员缺 TGI 则不参与加权 |
| 成员分类键 | 商品档案的 `category_l1` / `category_l2` / `category_l3`，按「品类名出现在层级路径中」匹配 |

未接入的层级（系列／爆款／IP）需要**聚合口径表**（`data/tables/aggregate-groups.csv`，见 §12.8）。该表到位后 `series`／`hot`／`ip` 层级按上述同一口径聚合；表未到位时相关调用返回 `data-not-ready`。

聚合口径表**未到位**时，非 `category` 层级返回 `data-not-ready`；表已到位但该键下没有带画像的商品时返回 `not-found`（不返回空结果）。

## 6. 年龄归并规则

统一目标档：`18-23 / 24-30 / 31-40 / 41-50 / 50+`

| 平台 | 源档数 | 说明 |
| --- | --- | --- |
| 抖音 | 10 | `18-19 / 20-23 / 24-30 / 31-35 / 36-40 / 41-45 / 46-50 / 51-55 / 56-59 / 60+` |
| 天猫 | 9 | 闭区间写法 `[18,24]` … `>=60` |
| 京东 | 13 | `0~15岁` 起，含 `61~65岁`、`66~70岁`、`71岁及以上` |

### 6.0 各平台的维度可用性

六维主干在三个平台的**源数据可用性并不相同**：

| 维度 | 抖音 | 天猫 | 京东 |
| --- | --- | --- | --- |
| 预测性别 | ✓ | ✓ | ✓ |
| 预测年龄段 | ✓ | ✓ | ✓ |
| 策略人群 | ✓ | ✓ | ✓ |
| 消费能力 | ✓ | ✓ | ✓ |
| 城市等级 | ✓ | ✓ | ✓ |
| **预测人生阶段** | ✓ | ✓ | **源数据无此维度** |

京东画像导出中**没有人生阶段类标签**，因此该维度在京东侧不存在投影数据——这是**源数据缺失**，不是目录登记遗漏。匹配计算时该维度按缺失处理，不做跨平台补齐。

### 6.1 精度标记

| 精度 | 含义 | 处理 |
| --- | --- | --- |
| `exact` | 源档完整落在目标档内 | 直接累加 |
| `partial` | 源档跨目标边界，或边界口径与其他平台冲突 | 累加 + 标记 `precisionLoss` |
| `lossy` | 语义近似但不完全等价 | 同上 |
| `unmapped` | 无对应目标档 | **不投影**，记 `unmapped-value` |

### 6.2 两类已知损失

**下界以上冲突（50 岁）**：50 岁在抖音与京东计入 `41-50`，在天猫计入 `50+`。三个相关源档位**一律标 partial** 并在 note 写明，不做人为统一，也不静默取一。

**下界以下缺口（京东 16-17 岁）**：统一词表没有低于 18 的落点。这类规则**不设 spill**，只标 partial 并写明缺口——设一个与源区间无交集的 spill 是错误标注。

### 6.3 spill 的含义

`spill` 表示源档**部分落入**的次要目标档，仅在源档真的跨入该档时设置：

| 例 | spill | 拆分比例 |
| --- | --- | --- |
| 天猫 `[18,24]` | `24-30`（闭区间上界 24 落入） | 6/7 与 1/7 |
| 京东 `16~20岁` | 无（16-17 无落点，并入最近档 `18-23`） | 全部进 `18-23`，标 `partial` |

`spill` **在投影中被真正消费**，按 §4.5 的区间重叠比例拆分，不是只记录不使用。

## 7. 缺失、冲突与问题清单

### 7.1 问题类型

| 类型 | 触发 | 严重度 |
| --- | --- | --- |
| `unmapped-dimension` | 原生维度未登记到统一维度 | warning |
| `unmapped-value` | 标签无已确认映射／档位无对应目标 | warning |
| `missing-field` | 主键列缺失，无法解析 | **error** |
| `conflict` | 同主键多行（SKU 级去重）、跨平台画像冲突 | warning（`manual` 处置为 error） |
| `entity-alias` | 画像实体名按别名目录归一 | warning |
| `scope-excluded` | 记录落在 README 声明范围之外，已跳过 | warning |
| `parse-error` | 文件为空、只有表头无数据行、sheet 不存在、占比列无法解析出任何数值、底层库无法解析文件 | **抛 `NormalizationError`**（不返回空结果） |

### 7.2 索引构建时的记录

| 情形 | 处理 |
| --- | --- |
| 数据根目录不存在 | **抛错**，不返回空索引 |
| 数据根下没有可扫描子目录 | **抛错** |
| 未识别的数据文件 | 记 `parse-error`（warning）issue，**不静默跳过** |
| 同一款号出现在多张商品表 | 记 `conflict` issue，**保留先到的一条，不做隐式合并** |
| 画像文件缺月份信息 | `month` 为空串，不推测 |
| 画像无样本量／覆盖率 | 抖音／天猫／京东的画像导出均无这两个字段，工具返回中相应键为 undefined，**不补默认值** |

### 7.3 结构性错误必须抛出

以下情况**抛 `NormalizationError`**，不返回带空结果的画像：

| 情形 | 错误类型 |
| --- | --- |
| 文件为空 | `parse-error` |
| 只有表头没有数据行（三平台画像、商品表、渠道表） | `parse-error` |
| sheet 名不符（如天猫的 `明细` 缺失） | `parse-error` |
| 缺必要列（维度列／标签列／占比列） | `missing-field` |
| 占比列**全部**无法解析为数值 | `parse-error` |
| 底层库无法解析文件（如 0 字节 XLSX） | `parse-error`（原始库错误被包装） |
| 商品／渠道表缺主键列 | `missing-field` |

**部分行类型不符**（占比列有部分行解析不出）不抛错：可解析的行正常投影，无法解析的行跳过，并记 `parse-error`（**error** 级）说明跳过了多少行。

### 7.4 占比是必填项，TGI 是可选项

三平台的画像都有占比列，TGI 列只有抖音与京东有。因此判定口径是：

| 字段 | 缺失时 |
| --- | --- |
| 占比 | 该行**不可用**，跳过并计入 `parse-error`；整列都不可用则抛错。**不因 TGI 正常就伪造 `share: 0`** |
| TGI | 该项不落位，投影中无 `tgi` 字段；**不补 0** |

### 7.5 文件不存在不是解析错误

文件不存在时抛标准 `ENOENT`（`error.code === 'ENOENT'`），**不包装成 `parse-error`**——文件找不到是调用方问题，与文件损坏是两回事。

**理由**：下游必须能区分「文件坏了」与「该月无画像」。前者是数据管道故障，后者是正常的空结果。静默返回空结果会让前者被当成后者，在跨期对比中制造假象。

### 7.6 缺失处理原则

| 情形 | 处理 |
| --- | --- |
| 某个标签缺失 | 不补 0，不插补，该标签在投影中不存在 |
| 某个维度缺失 | 不投影该维度 |
| 某个月份缺失 | **不回退到相邻月份**，查询时明确报「该实体在 X 月无画像」 |
| 未登记的源列 | 进 `extra`／`attributes`，不丢数据 |

### 7.7 缺月不回退

抖音工具（`app.js`）在缺月时回退到该实体最新月份。本项目**不沿用**：回退会把「这个月没数据」伪装成「这个月有数据」，在跨期对比中制造假象。

P1 匹配计算若需要「取最近可用月」，该口径在 P1 单独定义，不污染 MCP 层。

## 9. 背对背隔离

### 9.1 排除清单

`packages/core/src/product/catalog/fields.ts` 中 `usage` 不含 `prediction` 的字段**不得进入预测路径**。其中商品部人工定位字段 8 个：

`target_age` 年龄段 · `product_positioning` 商品定位 · `promo_group` 推广群组 · `product_group` 商品群 · `scene` 场景 · `extension` 延续款 · `theme` 主题 · `story_line` 故事线

另有 `fab`（人工撰写的卖点表述，含 Benefit 层话术）一并排除——预测如需使用应改用独立的版型／面料／工艺列。

**未登记的字段默认排除**在预测路径之外（fail-closed）。

> **注意**：`ProductDossier.attributes` 是**完整字段集**，包含人工定位字段——它是档案，不是预测输入。预测路径必须只用 `predictionAttributes`（已剔除被排除字段）。直接取 `attributes` 会绕过隔离。

### 9.2 校验方式

- `FieldCatalog.isExcludedFromPrediction(key)` 返回是否禁止
- 归一化输出中 `predictionAttributes` 已剔除被排除字段
- 测试断言 8 个人工定位字段**全部**落在 `comparisonOnly` 且不出现在 `predictionAttributes`

### 9.3 性别修正

`gender_correction` 属**从历史成交回算的事实修正**，不是人工画像，允许进入预测路径。但新款预测**不得使用该款自身的修正值**，应从同类历史款推算。该约束目前由字段 note 记录，**尚未在类型层面按来源强制**，属已知限制（见 result.md）。

- 渠道经营指标 → `ChannelRecord.performance`（`成交额`→`gmv`、`成交件数`→`orderCount`、`转化率`→`conversionRate`、`客单价`→`aov`、`毛利率`→`grossMargin`）

- 零售额与零售量齐全时推出**真实成交单价**（`resolveUnitPrice`，按月优先）：该月零售额与零售量均 > 0 → `零售额 ÷ 零售量`；否则主数据 `actualUnitPrice`，否则 `unitPrice`；缺失不插补、不把按月指标写回主数据 `price`
