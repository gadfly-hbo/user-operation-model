## 1. 我们要造什么

三条需求，对应三个交付物：

| # | 需求 | 交付物 | 形态 |
|---|---|---|---|
| 1 | 从消费者视角认识人、货、渠 | **数据 MCP** | 本地 MCP Server（stdio），暴露人/货/渠画像查询能力 |
| 2 | 模型一：货与渠匹配 | **工具1**（抖音范式）+ **工具2**（ModelEvol 范式） | 工具1 = 规则匹配看板；工具2 = 可版本化的匹配模型 + 报表 |
| 3 | 模型二：留存与回购 | **报表集** | 本地自包含 HTML + Excel |

**贯穿三条需求的一条主线**：把人、货、渠三侧画像统一成同一套"标签维度 + 占比 + TGI"的数据契约，让商品部的经验画像和会员部的算法画像可以在同一坐标系里比对——这就是业务方案里"背对背预测、面对面校对"能落地的前提。

### 硬约束

- **数据不上云**：所有数据文件、模型工件、报表产物全部留在本地进程与本地文件系统；不引入任何外网出网请求。
- **本地优先**：全部通过 `127.0.0.1` 或 stdio 调用，不做公网暴露。
- **可离线**：断网状态下工具链必须完整可用。

## 2. 总体架构

```
                    ┌─────────────────────────────────────────┐
                    │   人群运营模型工作区（本地，单仓库）      │
                    │                                          │
  客户数据源 ─────► │  ┌────────────────────────────────────┐  │
  (本地文件)        │  │ 数据层 data/                        │  │
                    │  │  归一化后的人/货/渠画像 + 经营指标  │  │
                    │  └───────────────┬────────────────────┘  │
                    │                  │ 只读                    │
                    │      ┌───────────┴───────────┐          │
                    │      ▼                       ▼          │
                    │  ┌────────┐          ┌──────────────┐   │
                    │  │ 数据MCP │◄─────────│ 工具1 / 工具2 │   │
                    │  │ (stdio)│          │   + 报表集    │   │
                    │  └────────┘          └──────┬───────┘   │
                    │                            │           │
                    │                            ▼           │
                    │                    ┌───────────────┐   │
                    │                    │ model-mlflow  │   │
                    │                    │ (模型登记/评估)│   │
                    │                    └───────────────┘   │
                    └─────────────────────────────────────────┘
```

**关键架构判断：工具1 和工具2 不是两个独立工具，而是同一条链路的两个入口。**（已决策 D1）

| | 工具1 | 工具2 |
|---|---|---|
| 输入的商品画像 | **已有的真实成交人群画像**（抖音/天猫导出） | **商品属性**（FAB/版型/面料/价格带） |
| 画像来源 | 事实数据 | 算法预测 |
| 回答的问题 | 「这批货该配哪个渠道」 | 「这批货会卖给谁、该配哪个渠道」 |
| 覆盖范围 | 已上市有成交的款 | **未上市的新品** |
| 对应业务环节 | 面对面校对 | 背对背预测 |
| 技术范式 | 专家规则评分 | 可训练 + 可版本化的模型 |

这个分工不是我们发明的，是业务方案里"背对背"机制的必然要求：会员部要在**看不到商品部人工画像**的前提下独立预测，只能从商品属性出发。所以工具2 必须具备"属性 → 画像"的能力，否则背对背无从谈起。

**两个工具共享同一个匹配内核**：画像 → 六维匹配分 → A/B/C 评级。差异只在画像从哪来（事实 vs 预测）。这也意味着 ModelEvol 的 `fit-method.mjs` 与抖音工具的 `app.js` 应该收敛成同一个包的两条输入路径。

## 3. 需求一：数据 MCP

### 3.1 数据域设计

按《零售服饰人群运营模型》第一章的三段结构设计，落到具体数据实体。

#### 渠道画像（渠）

- **渠道信息**：渠道 ID、渠道类型（直播 / 商品卡 / 短视频 / 天猫 / 京东 / 线下门店 / 私域小程序 / 唯品会特卖 / 奥莱）、渠道定位、平台人群画像、所属层级（品牌 → 渠道 → 账号）
- **渠道人群画像**：与商品侧**完全相同的维度集**，标签 + 占比 + TGI + 样本量 + 画像覆盖率 + 统计月份
- **渠道经营指标**：成交额、成交件数、件单价、转化率、客单价、流量成本（部分渠道缺）、毛利率

#### 货品画像（货）

- **单品基础信息**：SPU 款号、商品 ID、名称、品类（一级/二级）、季节、上新类型、价格（吊牌价 / 企划件单价 / 零售额 / 零售量 / 真实成交单价）、件数、版型、面料成分、设计工艺、IP/联名、FAB 三层拆解（Feature / Advantage / Benefit）
- **货品人群画像**：
  - 单款人群画像（各维度 share + TGI）
  - 品类人群画像（聚合）
  - 系列人群画像（聚合）
  - 爆款人群画像（聚合）
  - IP 人群画像（聚合）
- **生命周期行为漏斗**（对应方案三阶段）：
  - 上新期 T+0~30：浏览、收藏、加购、购买、直接购买
  - 增长期 T+31~75：收藏、加购、购买、直接购买、退货
  - 清仓期 T+76+：购买、退货
- **经营指标**：零售额、零售量、零售折扣、毛利率、退款率、退货率、UV、转化率、售罄率、缺码率、UPT、新老客占比

#### 人群画像（人）

- **品牌目标人群画像**（企划定义的目标）
- **品牌全域人群画像**（实际成交沉淀）
- **竞品人群画像**
- **会员特征字典**（方案 §5.2 的字段集，是最精细的一层）
  - 体型版型：主力穿着尺码、版型宽容偏好、尺码退货敏感度
  - 风格审美：主风格圈层、色彩接受度、设计细节敏感度、IP 偏好
  - 时令节律：新品尝鲜倾向、跨季换新心智、生命周期状态、连带穿搭潜力
  - 价格渠道：折扣敏感度、首选成交渠道、全域流转特征
  - 行为派生：RFM 属性、类目偏好、渠道偏好

### 3.2 统一标签维度集

这是三个域能对话的关键。**商品侧、渠道侧、人群侧共用同一套维度命名**，否则匹配分无从计算。

沿用抖音与 ModelEvol 已经验证过的六维主干：

| 维度 | 标签类型 | 说明 |
|---|---|---|
| 预测性别 | 分类 | 男/女占比 |
| 预测年龄段 | 分类 | 抖音原 10 档 → 归并 5 档（18-23 / 24-30 / 31-40 / 41-50 / 50+），另保留原始档位 |
| 八大消费群体 | 分类 | 策略人群 |
| 预测消费能力 | 分类 | 低/中/高消费占比（客单承接的输入） |
| 城市等级 | 分类 | 一二三四线 |
| 预测人生阶段 | 分类 | 学生/职场/家庭等 |

补充维度（方案 §5.2 的风格/价格/渠道类）在会员特征字典层落地，暂不进入首版匹配分。

**统一表示**（沿用抖音工具已有的解析结构，可直接复用）：

```ts
type Portrait = {
  dimension: string;      // "预测年龄段"
  labels: Record<string, { share: number; tgi: number }>;
};
```

### 3.4 技术形态

- **协议**：MCP over stdio，本地进程启动，无网络监听。
- **实现语言**：TypeScript / Node 22（与 model-mlflow 同构，见 §6）。
- **数据层**：只读挂载本地数据目录，索引在内存（规模：万级商品、数十渠道、百级标签 → 单文件 JSON 索引足够，无需向量库）。

**待确认（阻塞项）**：数据源的具体形态——导出格式、是否按月分文件、字段命名是否与抖音/天猫一致。这直接决定归一化层的工作量。见 §9 开放问题 Q1。

## 4. 需求二：两个工具

### 4.1 工具1 —— 规则匹配看板（参考抖音货渠匹配）

**定位**：不训练、开箱即用、给商品企划和渠道操盘手做日常选品排期。

**核心逻辑**（沿用抖音工具 `app.js` 的评分规范，六维加权）：

```
维度分 = max(下限, 100 - 距离系数 × 分布距离)
综合分 = Σ(维度分 × 权重) / 权重和 + 客单惩罚，裁剪到 [25, 99.5]
评级：A ≥ 80 | B 60–79.9 | C < 60
```

**首版必须修的三个问题**（都是抖音工具的现存缺陷）：

1. **地域同频、品类共振两个维度是写死的 85 / 84**（`app.js:199-204`）。新工具要用真实算法。建议取 ModelEvol `baseline.ts` 的 **weighted Jaccard** 与抖音 demo 的 **Top-N 标签 Jaccard** 做交叉验证。
2. **TGI 被解析展示但不参与评分**。TGI 恰好是"相对某基准的偏好度"，正是跨品牌/跨渠道对比的正确量纲。建议把匹配分升级为 **TGI 空间计算**（TGI 加权距离），而非只在 share 空间算。
3. **权重硬编码 + 评级门槛在界面上可调但代码写死**（`app.js:872-898`）。全部参数化到配置文件。

**客单承接规则**（抖音工具最成熟的部分，原样保留为可配置表）：

| 商品价格 | 渠道条件 | 维度原始分 | 全局扣分 |
|---|---|---:|---:|
| < 100 | 无条件 | 95 | 0 |
| 100–199 | 无条件 | 88 | 0 |
| 200–399 | 高消费占比 ≥ 28% | 92 | 0 |
| 200–399 | 高消费占比 < 28% | 70 | -3 |
| 400–499 | 高消费占比 ≥ 34% | 90 | 0 |
| 400–499 | 高消费占比 < 34% | 58 | -6.5 |
| ≥ 500 | 高消 ≥ 38% 且低消 ≤ 32% | 93 | 0 |
| ≥ 500 | 高消 < 25% 或低消 ≥ 45% | 32 | -10.5 |
| ≥ 500 | 其他 | 68 | -4 |

**双维度匹配方法**（比抖音工具更进一步，参考 ModelEvol `fit-method.mjs`）：

单维度分 = **JS 相似度 60% + 余弦相似度 25% + Top3 标签重合 15%**，缺维度时对有效维度重归一化。这比纯 L1 距离更稳，且能输出"主要差异点"用于诊断。

**输出形态**（保留抖音工具的三视图 + 补齐 ModelEvol 的报表能力）：

1. **按渠道选品**：商品卡 + 匹配分 + 等级 + 诊断短句，可筛选排序
2. **一货配全渠**：单品在全部渠道的适配排名
3. **深度比对**：六维雷达图 + 客单断层预警 + 运营建议
4. **错配清单**（ModelEvol 2608 报告的核心价值）：按 `销售额 × (1 - 匹配分)` 排序的"高销售低匹配"清单 —— 这比按匹配分排序更接近真实的组货调整优先级
5. **交叉矩阵**：渠道 × 渠道匹配水位

**输出格式**：自包含静态 HTML（无外网依赖）+ 可选 CSV/Excel 导出。

**与 model-mlflow 的联动设计**：

model-mlflow（Model Pack Studio）的定位是**模型治理与产出**，不是在线服务。因此联动设计为：

```
训练侧：Studio 内通过对话训练 → 产出自包含 Node 模型包
         { model.mjs, predict.mjs, manifest.json, README.md }
                ↓ 精确版本复制（不带 mutable workspace 依赖）
本项目：src/models/human-goods-channel-match/vN/predict.mjs
                ↓
         import { predict } 或 node predict.mjs in.csv out.csv
```

具体规则：

- **精确版本锁定**：从 Studio Registry 查出目标版本号后复制 `workspace/exports/<name>/vN` 到本项目，**不直接依赖可变工作区**。
- **校验 `manifest.json`** 的 `formatVersion`、输入列、输出目标、数据指纹（`data_sha256`）。
- **Stage 以 Registry 为准**：`manifest.model.stage` 在晋级时不会回写（ModelEvol 那边 v7 DB 已是 Production，包内 manifest 仍写 Staging）。
- **在线接口需自建**：Studio 没有 `/predict` 端点。若需要 HTTP 暴露，本项目侧补一层薄适配（本地端口 + 令牌）。
- **模型契约对齐**：Studio 产物是 `predict(rows) → rows`，与本项目工具2 的 `商品属性[] → 六维画像` 输入输出形态天然契合。

|---|---|---|---|
| **A. 移植优先 ✅ 采用** | 直接移植 ModelEvol v0.4 + v0.6 的 Ridge 实现与训练管线，用用户数据重训，登记进 MLflow | 快、可控、结果可复现；先拿到"可对比的起点" | 训练能力固定，不随 Studio 演进 |
| **B. Studio 优先** | 在 Studio 里用对话重新训练，产出标准模型包 | 资产格式统一、纳入治理与评估 | 训练结果不可控，需要多轮人工验收 |

**A 路线的执行要点**：

1. 移植对象：`v0.6` 的训练管线骨架（prepare-dataset → make-folds → run-ablation → select-final → evaluate → validate）+ `v0.4` 的特征集与跨期验证协议。
2. 移植时必修：绝对路径改为配置注入、Ridge/解析/指标抽公共库、纳入类型检查、换成 exceljs。
3. 重训产出：仍按 Studio 契约导出为自包含 `predict.mjs`（`predict(rows) → rows`），登记进 model-mlflow。这样后续迁 Studio 时资产格式不变。
4. **验收线**：新模型必须在同一套跨期验证协议下**至少不低于 v0.4 的基线**（Top1 69.57% / Top3 91.55% / Share MAE 0.0825，23 款严格留出），否则不发布。
5. 演进留口：训练管线保持可插拔，后续可把"重训"这一步换成 Studio 训练，其他环节不动。

**业务侧产出（对应方案 §2.2 四大款式决策矩阵）**：工具2 的输出必须能直接映射到四类款式——共识款（双方重合度 ≥ 75%）、盲区款（算法看好经验看衰）、争议款（经验看好算法看衰）、异化款（人群定位完全错位）。这要求工具2 的输出不仅是六维画像，还要保留**与人工画像的可比结构**。

### 4.3 工具1 / 工具2 与数据 MCP 的关系

> **决策 D1：共享内核 + 两个画像入口。** 工具1 与工具2 不是并列的两个工具，而是同一个匹配内核的两种喂数方式。

```
数据 MCP ──(统一画像维度)──► 匹配内核 ──► 工具1（事实画像入口）
      │                            ▲
      └──(商品属性)──► 工具2 ──────┘  （预测画像入口）
```

匹配内核（共享，无状态，可单测）：

```
输入：商品画像 / 渠道画像 / 六维权重配置
输出：总分、A/B/C 级、各维度分、Top3 差异点、正负向驱动因素
```

## 5. 需求三：留存与回购报表集

**定位**：面向会员/数据部门 + 商品企划的双轨考核看板，方案 §5.3 的报表规格基本可直接落地。

### 5.1 报表清单

| # | 报表 | 内容 | 读者 |
|---|---|---|---|
| R1 | **月度大盘人群贡献结构表** | 首购新客 / 二回老客 / 成熟活跃老客 / 同季跨年老客 / 休眠流失召回客 × 买家数、占比、MoM、YoY、贡献 GMV、GMV 占比、AOV、件单价、UPT | 会员部、企划 |

| R3 | **老客来源时效穿透表** | Recency 1-30 / 31-60 / 61-90 / 91-180 / 181-365 / >365 天 × 回购人数、老客内占比、唤醒主推品类、主要购买渠道、平均毛利率 | 企划、渠道 |
| R4 | **老客跨渠道流转矩阵** | 来源渠道（线下门店/天猫京东/抖音快手/私域/特卖）→ 当月回购渠道 + 跨渠道回购率 | 渠道运营 |
| R5 | **清仓客次季跃迁表** | 季末清仓新客在次季新品的加购率、画像重合度、正价购买转化率 | 企划、财务 |
| R6 | **三大诊断面板** | 二回断崖 / 虚假繁荣 / 季前蓄水→季初爆发 | 管理层 |

### 5.2 三大诊断的判定逻辑（方案 §5.3）

1. **二回断崖**：大促引入大量新客，但第 60 天二回跃迁老客比例 < 10% → 判定首购客群低质或首购体验有缺陷，倒查 FAB 与版型。
2. **虚假繁荣**：老客回购数大幅上涨，但增长全部来自 Recency > 180 天的休眠召回客，且平均毛利率 < 30% → 判定过度依赖深折透支心智，正价健康回购未改善。
3. **清仓客次季跃迁**：清仓新客在次季正价新品的购买转化率 → 反向校验清仓打法的 LTV 价值。

三条诊断要在报表里以**红黄绿灯 + 归因结论**呈现，而非只有数字。

### 5.3 交互与输出

- 单页 HTML 报告（多 Tab：大盘 / Cohort / 老客 / 诊断），内联 CSS+JS，无外网依赖
- 图表用原生 SVG（参考抖音工具）或内联 ECharts
- Excel 多 sheet 导出（参考 ModelEvol 26Q4 预测包的多 sheet 做法）
- 数据由用户提供，走与数据 MCP 同一套归一化层

## 6. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | **TypeScript / Node ≥ 22.19** | ModelEvol 是 TS/Node，Model Pack Studio 产物是 `predict.mjs`（Node），抖音工具的 `app.js` 是 JS。单一语言 = 匹配内核可直接跨三个来源复用，模型包可直接 import |
| MCP | `@modelcontextprotocol/sdk`（TypeScript，stdio） | 官方 SDK，stdio 无网络暴露，天然满足"不上云" |
| 数据层 | 只读本地目录 + 内存索引；XLSX 用 exceljs（**不用 xlsx@0.18.5**，有高危漏洞） | 零外部依赖、离线可用 |
| 报表 | 自包含 HTML（内联 CSS/JS/SVG）+ Excel（exceljs 多 sheet） | 与 ModelEvol 报表形态一致，零外网依赖 |
| 图表 | 原生 SVG | 与抖音工具一致，零依赖 |
| 模型治理 | model-mlflow（Studio + MLflow 本地 SQLite backend） | 复用已有账本，不新建 |
| 训练 | Python（Ridge）→ 导出为 Node `predict.mjs` 契约；或直接用 Studio 训练 | 见 §4.2 路线 A/B |

**单一仓库布局**：

```
user-operation-model/
├── docs/                        # 本讨论稿、后续设计文档
├── packages/
│   ├── core/                    # 画像类型、匹配内核、评分配置、诊断规则
│   ├── data-mcp/                # MCP server（stdio），只读 data/
│   ├── tool1-channel-match/     # 规则匹配 → 静态看板
│   ├── tool2-model-match/       # 属性→画像→匹配，含 model-mlflow 客户端
│   └── reports/                 # 需求三报表集
├── data/                        # 原始数据（gitignore）+ 归一化产物
└── models/human-goods-channel-match/vN/   # 从 Studio 复制的精确版本模型包
```

> `packages/core` 是关键：匹配内核、维度定义、诊断规则**只写一份**，工具1 和工具2 都从它取。这是避免"两套评分口径"的技术保证。

```ts
type DimensionDiff = {
  dimension: string;
  productTop3: { label: string; share: number; tgi?: number }[];
  channelTop3: { label: string; share: number; tgi?: number }[];
  distance: number;            // 归一化距离
  overlapTop3: number;         // Top3 重合度
  jsSimilarity: number;
  cosine: number;
};

type MatchResult = {
  spu: string;
  channelId: string;
  totalScore: number;          // 0-100
  grade: 'A' | 'B' | 'C';
  dimensions: DimensionDiff[];
  dimensionScores: Record<string, number>;
  positiveDrivers: string[];
  negativeDrivers: string[];
  priceFit?: { band: string; penalty: number; warning?: string };
  confidence?: number;
};
```

### 7.4 匹配内核统一公式（工具1/工具2 共用）

```
单维度分 = 0.60 × JS相似度 + 0.25 × 余弦相似度 + 0.15 × Top3重合度
维度分   = 单维度分 × 100，缺维度时对有效维度重归一化
综合分   = Σ(维度分 × 维度权重) / Σ权重 + 客单惩罚
评级     = A (≥80) | B (60–79.9) | C (<60)
```

维度权重（初值，取 ModelEvol `fit-method.mjs` 的 `RAW_WEIGHTS`，上线前用实际数据重新校准）：

```
预测性别 0.10 | 预测年龄段 0.20 | 预测消费能力 0.15
城市等级 0.10 | 八大消费群体 0.25 | 预测人生阶段 0.20
```

## 9. 开放问题（需要拍板）

**Q1（阻塞 P0）· 数据源到底是什么？**
需要确认：① 来源系统与导出格式（巨量云图 / 电商罗盘 / 天猫数据银行 / 品牌自有 BI？）；② 文件组织方式（按月分文件还是累计表）；③ 字段命名是否与抖音/天猫一致；④ 商品主表与画像表用什么键关联（款号 / 商品 ID）；⑤ 历史跨度与数据量级。
> 这五项决定归一化层工作量，也决定维度集能否直接沿用。建议尽早给一份脱敏样本。

**Q2 · 工具1 与工具2 的关系定位？** → ✅ **已决策 D1：共享内核 + 两个画像入口**（事实画像入口 / 预测画像入口），工具1 相当于"工具2 喂入真实画像后的降级模式"。

**Q3 · 工具2 首版走移植路线 A 还是 Studio 路线 B？** → ✅ **已决策 D2：路线 A 移植优先**（移植 v0.4/v0.6 → 重训 → 登记 MLflow），Studio 训练链作为演进留口。

**Q4 · 匹配内核的六维与权重是否直接沿用？**
现用权重来自 ModelEvol 人工设定，**未经真实业务数据校准**。是否允许我们用用户提供的历史成交数据做一次回测校准（用售罄率 ≥ 0.6 且退货率 ≤ 0.12 定义"正匹配"，算 NDCG@K）？
ModelEvol 的 P0 已有这套评估设计，但回测数据未归档，需重建。

**Q5 · 首版是否需要交互式 Web 服务，还是静态产物即可？**
参考两个先例都是静态 HTML + 本地 server（127.0.0.1:8788 热更新）。静态产物更安全（无端口暴露），但改配置需重跑构建。

**Q6 · 报表是否需要 Excel 导出？**
ModelEvol 的 26Q4 预测包是多 sheet Excel + HTML 双份。业务侧拿去做汇报一般要 Excel，但 Excel 依赖有历史安全债。

**Q7 · 数据 MCP 的鉴权与并发？**
stdio 单进程无并发问题。若后续要多客户端（IDE + 脚本同时连），需要考虑文件锁与索引刷新策略。
