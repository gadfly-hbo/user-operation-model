## 0. 一句话结论

**数据底子是扎实的，产品骨架是缺的。**

归一化目录、匹配内核、背对背守卫、模板契约这些「难改的部分」做得对，应当保留；但整套东西是按「一次性查询工具 + 样本数据」搭的，没有按「按月运转、人来决策、留下痕迹的工作台」来搭。具体是五个结构性缺口：

| # | 缺口 | 一句话 |
| --- | --- | --- |
| 1 | **没有时间模型** | 档案是「快照」，经营指标、漏斗都塌缩成最新月；同一款多一个月画像，一半查询会静默变「没有」 |
| 2 | **身份关联靠字符串相等** | 画像和渠道对不上时没有任何提示（现有样本 6 份渠道画像 5 份是孤儿） |
| 3 | **没有服务层** | 17 个工具写在 MCP 闭包里，浏览器工作台用不了；匹配内核 MCP 调不到，Agent 只能跑命令行 |
| 4 | **「两个入口共享内核」只建了一个** | 工具2 包里没有任何内核调用，预测画像接不进匹配 |
| 5 | **没有决策留痕与验真闭环** | 评审、改判、决策、T+7 验真、权重校准——产品稿提了，底座里没有对应模型 |

建议**不推倒重来**，按 6 个切片演进出目标架构；前 3 个切片不需要真实业务数据，现在就能做。

## 2. 产品方向梳理

### 2.1 现在建的是什么

产品讨论稿 v0.1 把交付物定义成三件事：数据 MCP、工具1／工具2、留存回购报表集。这是**项目视角**（按交付物分），不是**产品视角**（按谁用来做什么分）。

后来的 [UI 设计说明](ui-design.md) 已经往产品视角走了一步：按「选品评审 → 货渠匹配 → 新品预测」的决策流程组织 9 个页面，并明确「选品评审台」是灵魂。但讨论稿没有随之更新，于是现在有两份方向文件：讨论稿 v0.1（三条需求、P0–P4）和 ui-design（工作台信息架构、6 个待拍板问题）。你这次说「最终打造成人群运营工作台」，等于把工作台定为产品形态——讨论稿需要升到 v0.2 来承接。

### 2.2 四类用户与他们的活儿

工作台要承载的主线，从业务方案和 UI 设计里能读出四类人：

| 用户 | 什么时候用 | 要做的决定 | 需要工作台给的 |
| --- | --- | --- | --- |
| 商品企划 | 季前企划 | 开哪些款、什么属性、首单多少 | 背对背预测、人工画像录入、面对面校对、四类款式动作建议 |
| 渠道运营 | 上新期、清仓期 | 哪批货配哪个渠道、组货怎么调 | 货渠匹配矩阵、错配清单、渠道画像 |
| 会员／数据部门 | 全周期 | 人群怎么唤醒、往哪个渠道引 | 标签反查、留存／Recency／流转、三大诊断 |
| 管理层 | 月度 | 看健康度 | 大盘人群结构、红黄绿灯与归因 |

### 2.3 产品层没想完整的事

| # | 问题 | 现状 | 影响 |
| --- | --- | --- | --- |
| P-1 | **工作台怎么运行**（讨论稿 Q5 未决） | 只有静态原型；真实数据版本只能命令行生成 HTML | 浏览器里的工作台读不到真实数据，这是所有后续工作的前提 |
| P-2 | **决策怎么留痕** | UI 设计提到 draft／override／attestation，底座没有数据模型和存储位置 | 「面对面校对」的结果无处安放，复盘无从谈起 |
| P-3 | **预测与匹配怎么验真** | T+7 验真、权重校准（Q4）只有零散提及 | 匹配分永远停在「未校准」，模型晋级没有依据 |
| P-4 | **默认看哪个月** | 各处各定：工具1 取渠道画像最新月；MCP 缺月报错；档案取最新月 | 同一款在不同页面可能不是同一个月的数 |
| P-5 | **画像怎么挂到渠道上** | 靠文件名与店铺名相等，对不上靠别名 CSV 补 | 关联失败是当前最大的数据问题，却没有提示、没有操作入口 |
| P-6 | **工具2 的位置** | IA 里占「新品预测」主位；模型门槛未过 | 用户会以为预测可信；需要降级呈现并写明晋级条件 |
| P-7 | **指标口径由谁定** | 指标字典 945 条是口径权威，但没有加载点 | P3 报表的口径只能靠人读字典；5 个口径问题悬着 |
| P-8 | **品牌范围** | 渠道覆盖多品牌，画像只属个别品牌 | 工作台是单品牌还是多品牌视角，未定义 |
| P-9 | **背对背怎么在产品里成立** | 只有 §9.2 的代码隔离（预测路径不读人工字段） | 缺「双方各自提交后才可见对方」的流程约束与凭证 |
| P-10 | **规模假设** | 万级商品、数十渠道、内存索引 | 够用；但索引每次进程启动重建，工作台需要刷新策略 |

### 2.4 建议的产品定义

> **人群运营工作台 = 本机运行的单用户决策工作台。** 它把人、货、渠的画像放到同一坐标系，支撑「背对背预测 → 面对面校对 → 款式分类 → 组货投放 → 生命周期验真 → 复盘校准」一条闭环；数据不出本机；Agent 通过 MCP 用同一套能力。

这一定义带来的架构要求：本地服务（非静态产物）、时间是一等公民、每个数字可溯源到文件与月份、决策可持久化、MCP 与浏览器共用一套工具。

## 3. 架构现状

```
site/web（静态原型，合成数据）              ←—— 没有后端
Agent 客户端 ──stdio──► packages/data-mcp（17 个 handler 写在 createServer 闭包里）
                              │ 只读
命令行 ──► packages/tool1 ────┤
命令行 ──► packages/tool2 ────┤
                              ▼
                   packages/core
                   ├─ index/     buildIndex（扫目录）+ query（线性查找）
                   ├─ normalize/  各平台解析 + 投影 + 12 张表
                   ├─ portrait/   维度目录、映射表、分档
                   ├─ product/    字段目录、档案类型
                   ├─ match/      内核（纯函数）
                   └─ model/      Ridge、指标、v0.4 训练
                              ▼
                   data/（只读，gitignore）
```

评价：**分层方向是对的**（core 纯、适配器薄），问题在「层里缺东西」而不是「层分错了」：

- `core/index` 同时承担「扫文件、识别文件、关联实体、裁剪范围、挂指标」五件事，都在一个 824 行的 `build.ts` 里
- `core/query` 把「选哪份画像」的策略（平台名排序、多月份返回空）藏在查找函数里
- 工具1 的 `dataset/` 里有一段本该属于领域层的编排：「这个月哪些商品 × 哪些渠道进矩阵、每家取哪份画像」
- `data-mcp` 是唯一对外入口，却只能给 Agent 用

## 4. 代码逻辑逐模块发现

严重度：**阻断**＝数据一到就出错或静默给错结果；**应修**＝口径不一致或有隐患；**建议**＝卫生与可维护性。标 ✅ 的已用合成数据探针实跑证实（附录 A）。

### 4.1 时间模型

| # | 级别 | 发现 | 证据 | 影响 |
| --- | --- | --- | --- | --- |

## 附录 C · 工具2 消费链路的接口事实

来源：审计子代理对照本机 v2 模型包整理；输入列与输出维度分布由主 agent 读 manifest 核实，映射关系未逐项复核。切片 E 起草前须复核。

- **输入 7 列**：`category`、`fabric`、`ipCollab`、`fit`、`productAttribute`、`season`、`specialFunctionMaterial`，取原值字符串。输出按输入下标对齐，不带 id；`predict.mjs` 另导出 `__contract` 供核对。
- **输出 32 列**：键为「天猫原生维度名__天猫原生标签」，每维合计 1。
- **与内核六维的对应**：

| 模型输出维度 | core 维度 | 内核是否消费 |
| --- | --- | --- |
| 预测性别 | `gender` | 是 |
| 预测年龄 | `age`（9 档与分档规则逐字一致） | 是 |
| 预测购买力 | `spending_power` | **否**（内核的消费能力走价格 × 渠道） |
| 预测城市等级 | `city_tier` | 是 |
| 大服饰策略人群 | `apparel_segment`（非主干） | **否** |
| 预测人生阶段 | `life_stage` | 是 |
| （模型不输出） | `strategy_segment` | 是，且权重最大（0.25） |

- **结论**：预测画像进内核时，五个分布维度只有四个可用，缺的恰是权重最大的一维。产品稿 §4.2 说工具2 的输出「不仅是六维画像，还要保留与人工画像的可比结构」，v06 模型实际做不到——这是切片 E 要如实呈现的限制，也是 P2-13 重训时要补的目标维度。
- **正确接法**：把输出装成 `platformLabels = { tmall: { 维度: { 标签: { share } } } }`，走既有 `projectPortraitLabels('tmall', …)` 投影，不手写映射。
- **字段名对照**：`fit`←版型、`category`←品类、`subcategory`←小类、`productAttribute`←货品属性、`ipCollab`←IP/联名、`specialFunctionMaterial`←特殊功能/材质。core 把「品类」「小类」都归到 `category_l3`，与模型的两级区分冲突。
- 可消费的只有 v06 包；v04 合规模型没有导出器。
