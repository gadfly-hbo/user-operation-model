# openspec — 变更记录目录

每项非平凡变更在 `changes/<change-id>/` 维护一份简洁规格与结果记录。流程要求见 [工程规范 §4](../docs/engineering-workflow.md#4-连续-sdd-与-tdd)。

## 目录约定

```
openspec/
└── changes/
    └── <change-id>/
        ├── spec.md           # 规格：目标、验收标识、范围、边界、检查计划
        ├── result.md         # 结果：实际交付、验证证据、失败与未验证项
        ├── implementation.md # 可选：实施过程记录、阶段清单更新
        ├── review.md         # 可选：独立复核记录
        └── <其他>.md         # 可选：专项证据（口径校准报告、对照分析等）
```

**change-id** 用小写英文加连字符，描述变更主题而非编号，例如 `data-mcp-core`、`tool1-channel-match`、`tool2-model-port`。不用纯序号——序号不携带信息。

## 什么时候建目录

| 情况 | 处理 |
| --- | --- |
| 简单、范围闭合的修复 | 不建目录；在适用原记录中留下复现、修正与验证 |
| 跨模块、影响 `packages/core` 匹配内核 | **必须**建目录 |
| 涉及数据契约、模型资产、公共接口、持久化结构 | **必须**建目录 |
| 纯文档整理 | 通常不建；但修改工程规范本身需要独立复核 |
| 新增依赖 | **必须**建目录，并在 spec 中记录出网路径核对结论 |

## spec.md 写法

最少写清：

- **完整可观察结果** —— 用外部可验证的行为描述，不写实现步骤
- **需求／验收标识** —— 编号的验收条目，便于复核逐项核对
- **范围与不做事项** —— 明确写出本次不做什么，避免范围蔓延
- **允许修改路径** —— 具体到目录或文件
- **关键边界** —— 数据边界、隔离约束、失败语义
- **适用检查计划** —— 会跑哪些检查、期望什么结果
- **未决问题** —— 需要用户决定的事项

同时写**任务目标执行清单**（见[规范 §4.5](../docs/engineering-workflow.md#45-任务目标执行清单与范围管理)）：顶部写明本轮目标与预期交付，下面按阶段拆任务，每项标注可核对的完成条件。

## result.md 写法

记录**实际发生的事**，不是计划：

- 交付了什么，对应哪条验收
- 实际跑了哪些命令／入口，结果如何（附证据位置）
- 失败项、跳过项、未验证项分别列出，状态用 `PASS` / `FAIL` / `NOT_RUN` / `UNKNOWN` / `NOT_PROVED`
- 与 spec 的偏差，如有须说明是用户批准的范围变更还是流程偏差
- 已知限制与后续点

**不改写 spec 中已确认的部分**。范围变更须由用户确认后，在 spec 内另起版本说明段（如 `### v0.2 ...`），保留原版本描述。

## 归档

变更完成后原位归档：保留 `spec.md` 与 `result.md`，不删除、不合并、不重命名。历史变更当时的 `FAIL` / `UNKNOWN` / `NOT_PROVED` 事实**不因后续修正而改写**——修正由新变更承接。

## 数据约束

变更记录中**不放业务数据**：不贴原始导出、不贴完整画像表、不贴报表产物。需要示例时用脱敏或合成的最小样例，体积控制在能说明问题的最小量。违反即按[规范 §7](../docs/engineering-workflow.md#7-数据不出网与副作用)处理。
